# Screens, Circuit and Metro

Use the `new-screen` skill to scaffold a screen. The rules it follows:

- A screen is a `@CircuitSerializable(<scope>::class) data object/class XScreen : Screen`, plus an `XState : CircuitUiState` with an `eventSink`, an `XEvent` sealed interface, a presenter and a UI. Screen args must be serializable: pass IDs and AT-URI strings, not views.
- Use the same scope in `@CircuitSerializable` and both `@CircuitInject`s. `SessionScope` is for signed-in screens. `AppScope` is only for signed-out ones such as login. A mismatched or missing registration compiles fine but crashes at runtime the first time navigation state is saved.
- The presenter is a `@CircuitInject(XScreen::class, <scope>::class) @Composable fun XPresenter(screen, navigator, ...deps): XState`. Circuit supplies `screen`/`navigator`, and Metro injects the rest. Don't write a presenter class with `@AssistedInject`. A class with plain `@Inject` is fine only when it needs neither screen nor navigator (like `LoginPresenter`).
- The UI is `@CircuitInject(XScreen::class, <scope>::class) @Composable fun XUi(state: XState, modifier: Modifier = Modifier)`.
- **One screen spans three modules, all in the same feature package `io.github.solcott.activitytracker.app.<pkg>`:** `XScreen.kt` (Screen, State, Event) in `app/screens`, `XPresenter.kt` in `app/presenters`, and `XUi.kt` in `composeApp`. Presenters and UIs see each other only through the contracts. `:app-presenters` has the Compose runtime and, through `:app-screens`, foundation, but only for `TextFieldState`: no material3 and no UI code (layouts, modifiers, emitting composables). `composeApp` depends on `:app-presenters` only so its graphs aggregate the factories. Never import a presenter from UI code. Shared composables (`ui/`, `ActivityTypePicker`) and `expect` UI helpers (`LocationPermission`) stay in `composeApp`.
- **Text fields** take a `TextFieldState`, never the `value` + `onValueChange` overloads (`String` or `TextFieldValue`). When the presenter needs the text (to save, validate or search), it owns the state: `rememberTextFieldState()` in the presenter, a `TextFieldState` field in `State`, no `XChanged(String)` event. The presenter reads `.text` when it acts, fills a loaded value with `setTextAndPlaceCursorAtEnd` and empties it with `clearText`; tests edit the state the same way. Reading `.text` in a `State` getter (`valid`) or in the presenter's composition keeps it live. Text only the UI uses (a picker's search box) is a `rememberTextFieldState()` in the UI. A `readOnly` field showing a value takes `rememberReadOnlyTextFieldState(text)` (`ui/`). Use `lineLimits = TextFieldLineLimits.SingleLine` and `onKeyboardAction`, not `singleLine`/`keyboardActions`, and an `InputTransformation` to react only to typing (opening a menu). detekt's `UseTextFieldState` rule (`:detekt-rules`) enforces this; it can't see types, so name every argument after the state.
- **Platform look.** Build UIs from `ui/adaptive` (`AppScaffold`, `AppTopBar(title, onBack = ...)`, `AppButton`, `AppTextField`, `AppMenu`, `AppIconButton(AppIcon.X, ...)`…), not Material's `Scaffold`, `TopAppBar`, buttons, text fields, progress indicators, sheets or dialogs; detekt's `UseAdaptiveComponents` flags those. Give a screen `onBack` even if it can be a tab root: `AppTopBar` hides the button at the root (`LocalIsNavRoot`). Lists go in `ReadableList` (centred column and scrollbar on desktop and web), and scrolling forms take `Modifier.readableWidth()` inside a `ScrollbarBox`. Pass `AppScaffold`'s padding to them as content padding (`ReadableList(contentPadding = padding)`, or `.padding(padding)` after `verticalScroll`), never as a `Modifier.padding` around the scroll, so content scrolls under the bars. A scrolling screen also gives its bar a `rememberAppTopBarScrollBehavior()` and puts its `nestedScrollConnection` on the `AppScaffold` (on the list, inside pull to refresh): the bar then marks content scrolled under it, and a tab root's large title collapses on iOS. Branch on `LocalUiPlatform` only for real differences in behaviour, like pull to refresh on phones or Android's Record FAB. A new full-screen flow also joins `TopLevelDestination.FullScreenFlows`.
- **Text.** Every string a UI shows (labels, content descriptions, units, counts) lives in `composeApp/src/commonMain/composeResources/values/strings.xml` and is read with `stringResource`/`pluralStringResource` from the generated `io.github.solcott.activitytracker.composeApp.resources.Res`. Use `<plurals>` for counts. Shared helpers: `sportLabel`/`activityTypeLabel` (looked up by token as `sport_<token>`/`sub_sport_<sport>_<token>`), `handleLabel` (`ui/Labels.kt`) and the composable unit formatters in `Format`. Presenters can't read resources, so a failure goes in `State` as a `UiError(kind, detail)` (`:app-screens`), never a `String`. Add a `UiError.Kind` and its string, and the UI shows it with `errorText`.
- Metro generates the Circuit factories (`metro.enableCircuitCodegen=true`). There is no Circuit KSP processor, so don't add one.
- **Sub-screens (SubCircuit).** For a reusable piece of a screen with its own presenter and UI (a filter bar, a picker), use `circuitx-subcircuit`, not a screen or a plain composable. It is opted in module-wide (`ExperimentalSubCircuitApi`). The session's `SubCircuit` is built from Metro-multibound `SubPresenterFactory`/`SubUiFactory` sets (`CircuitBindings.kt`) and provided as `LocalSubCircuit` in `App.kt`. There's no `AppScope` one yet. It spans the same three modules and package as a screen:
  - **Contract** (`app/screens`): an `@Immutable` `XScreen : SubScreen<XOuterEvent>`, an `XState : SubCircuitUiState` with an `eventSink`, an `XEvent` and an `XOuterEvent : SubCircuitOuterEvent` sealed interface. The screen carries only initial config, never live state: `SubCircuitContent` remembers the presenter per screen and keys its content on it, so a changed screen remounts the child and drops its state.
  - **Presenter** (`app/presenters`): a `@SubCircuitInject(XScreen::class, <scope>::class) @Inject class XPresenter(screen: XScreen, ...deps) : SubPresenter<XOuterEvent, XState>`, a class because SubCircuit has no function form. Metro injects the screen (leave it out if unused); no `@AssistedInject`. There's no navigator. It seeds its state from the screen (`rememberRetained { mutableStateOf(screen.initial) }`) and reports it with a keyed `SideEffect(value) { outerEventSink(...) }`, which also fires when first shown, so the host matches it even after one side lost its state.
  - **UI** (`composeApp`): a plain `@Composable fun XUi(state: XState, modifier: Modifier = Modifier)`, registered by a `@SubCircuitInject(XScreen::class, <scope>::class) @Inject class XSubUi : SubUi<XState>` whose `Content` calls `XUi`. Don't put `@SubCircuitInject` on the function. Metro accepts it, but the factory it generates holds a function reference that crashes the Kotlin/Wasm backend (`UpgradeCallableReferences`, `IndexOutOfBoundsException`). JVM, Android and iOS compile it fine, so only a wasm build catches it.
  - **Host**: `SubCircuitContent(state.xScreen, outerEventSink = { state.eventSink(Event.XChanged(it...)) })` in the UI. The host presenter creates the screen once (`rememberRetained { XScreen(initial) }`) and keeps what it needs from outer events in its own state; it replaces the screen only to reset the child. Parent and child talk only through the screen (down) and outer events (up).
  - **Tests**: `circuitx-subcircuit-test`'s `presenter.test { awaitItem(); outerEvents.awaitEvent() }` in `app/presenters/src/jvmTest`.
- **Event-driven work goes through `rememberSingleFlight()`** (`:app-presenters`), never a bare `rememberCoroutineScope()`: `flights.launch(key) { ... }` drops a repeat while the first runs, so a double tap can't save, follow or give kudos twice. The key is the event (`XEvent.Save`, `XEvent.Changed::class` for one with args) or what it acts on (an activity's URI for its kudos). Derive a `saving`/pending flag from `flights.isRunning(key)` instead of a separate `var`, and use `launchLatest` only when a newer request should replace the running one (a new file pick). Loads stay in `LaunchedEffect`. detekt's `UseSingleFlight` rule flags `rememberCoroutineScope()` in `*Presenter.kt`. A presenter test for a write sends the event twice while the first is in flight (gate the fake's response) and asserts one write (`ProfilePresenterTest`).
- Wrap suspend calls in `runSuspendCatching`, not `runCatching`, so cancellation propagates. Writes go through repositories (`ActivityRepository` → outbox), never straight to XRPC from a presenter.
- **Graphs.** `AppScope` is app-wide. `SessionScope` is the `SessionGraph` extension created per signed-in account (`key(did)` in `App.kt`). The concrete `@DependencyGraph`s are `AndroidAppGraph`/`IosAppGraph` in `composeApp` platform source sets and `WebAppGraph` in `webApp`. A module that declares a graph needs every contributing module (including `:app-screens` and `:app-presenters`) on its compile classpath. `androidApp` can't use Metro intrinsics; it calls `createAndroidAppGraph` from `composeApp`.
- **Stability.** Every `State` is `@Immutable`, and its collections are `ImmutableList` (kotlinx-collections-immutable; convert with `toImmutableList()` where the presenter loads them), never `List`. Models from non-Compose modules that a UI shows (lexicon views, `AuthCoordinator.Status`) carry `@Immutable` from `androidx.compose.runtime:runtime-annotation`. Composable params must be statically stable, so pass `ImmutableList`s and annotated types, not `List`, `vararg` or plain interfaces (`@Stable` it if one must be a param, like `AppGraph`). `composeStabilityCheck` (part of `check`) enforces this from the compiler reports in `build/compose/reports`; `:app-screens` also runs it in strict mode, which fails on any field that isn't statically stable.
- **Tests.** Presenter tests live in `app/presenters/src/jvmTest` and use `circuit-test`'s `Presenter.test {}` with a Room `inMemoryDatabase()` and a Ktor `MockEngine` (see `LoginPresenterTest`).
