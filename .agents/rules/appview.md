# AppView

- **The AppView never writes to repos or spaces. It holds non-public activities, by tier, and likes and comments on them, and nothing else private.** It reads Jetstream for public records, syncs athletes' tier spaces for non-public activities and their `interactions` spaces for likes and comments on them (below), and serves `app.activitytracker.*` queries. From tier spaces it stores only `feed.activity` and `feed.activityStreams`, and from `interactions` spaces only `feed.like` and `feed.comment` (`Indexer.spaceCollections`): never `actor.privateDetails`, `graph.followDecline` or `actor.activityDefaults`. Profile details an athlete marks Followers, Mutuals or Only me stay in their tier spaces, which clients read directly, so views show only the profile record's details (`publicDetails`, `api/ActorDetails.kt`). The indexer validates those with `ProfileDetailRules` and drops what breaks a rule. Treat the database and its backups as holding private data.
- **Every activity read is filtered by tier.** `activities.visibility` is the tier a row is served at (`public` for the repo, else its space's key), and `visibleTo(viewer)` (`api/TierAccess.kt`) ANDs into every activity query: timeline, author activities (both orders), `getActivity` (a hidden activity is `NotFound`), `getLikes`, recordings and `activitiesCount`. It admits readers as `SpaceAccess` does, from effective follows; an unknown tier is the athlete's only, and a null viewer sees public rows. Likes are checked at serve time for their giver too: `hydrate`'s counts and `getLikes` join likes to the activity (`admittedLikes`) and apply `visibleTo(Likes.authorDid)`, the per-row form, so a like counts only while its giver may see the activity at its current tier, wherever the like is stored (repo or the giver's `interactions` space, `likes.origin`). Comments get the same giver check plus their audience: `hydrate`'s counts and `getActivity`'s list join comments to the activity (`admittedComments`) and apply `commentsVisibleTo`, which is `visibleTo(Comments.authorDid)` and `visibleTo(viewer)` against `comments.audience` (the visibility the comment was written for, normalised at index time: absent is `public`, unknown is `self`). Tiers nest, so a comment shows at the narrower of the activity's current tier and its audience: it follows a narrowing, but a widening never shows it wider than written. `comments.origin` scopes deletes and `dropSpace` like `likes.origin`. A recording counts (hidden from feeds, listed under its primary) only at its primary's visibility.
- **Activities have one URI wherever they're held.** A space-held activity is indexed at `at://{did}/app.activitytracker.feed.activity/{rkey}`, like a repo one, with `origin` = `repo` or the space URI. Mid-move one URI has two origins: the narrower tier's copy is the row, the other waits in `record_shadows`, and a delete removes only its own origin's copy, promoting the shadow (`Indexer.place`/`delete`). Streams work the same way (`activity_streams.record` keeps the raw record for that).
- **Activity streams are served only through `ActivityStreamsViews`.** `getActivityStreams` checks the row's visibility (the record's own field for repo records, capped at the tier for space ones; unknown values mean `self`), hides streams whose indexed activity the viewer can't see, and strips zones unless the viewer is the athlete or the athlete's training is public. Their data blob comes through `StreamSource` (the repo's PDS, or the space as a member) and is cached by CID in `activity_stream_data`.
- **`checkUserAccess` is the managing-app callout.** An athlete's PDS calls it before issuing a credential to one of their `app.activitytracker.space.athlete` spaces. Its tokens are addressed to `managingAppService` (`<serviceDid>#activitytracker_space`), so the route uses the separate managing-app verifier (`verifier.forAudiences`), and AppView tokens never work there or the reverse. `SpaceAccess` decides by tier (`AthleteSpace` skey): `public` admits anyone, `followers` uses `follows` (an effective follow of the athlete, also the rule for Followers streams), `mutuals` uses `isMutual` (effective follows both ways; both in `api/ActorDetails.kt`, also the rule for Mutuals streams), and everything else, every `write` and an issuer other than the space's authority are denied. The AppView's own DID may read all four tiers, `self` included, and the `interactions` space (which admits no one else), so it can sync them; it's denied `write` and unknown keys like anyone. A denial is `200 {"authorized": false}`, never an error.
- **Only effective follows count.** An athlete whose profile has `followPolicy: approve` (stored as `actors.follow_policy`; any other value is null, meaning open) counts a follow only once they publish a `graph.followApproval` for the follower. Every query that reads `follows`, except for the viewer's own follow record (`viewer.following`), ANDs in `effectiveFollow()` (`api/ActorDetails.kt`): timeline authors, counts, follower and follow lists, `follows`/`isMutual`. The indexer keeps an approval only at rkey = its subject's DID, so there's one per pair and deleting it removes the follower. `getFollowRequests` lists the pending ones, declined included: declines live in the athlete's `self` space and never reach the AppView.
- **Repos are untrusted input.** The `Indexer` decodes with the shared `AtJson` models, drops records that fail to decode (it catches `IllegalArgumentException` and `SerializationException`), and truncates free-text columns with `.take(n)` so they fit the column. New record handlers do the same.
- **Indexing is idempotent.** Every write is an upsert or delete keyed by AT-URI, so rewinding the Jetstream cursor replays safely. Never use a plain `insert` for record rows. Every new record table also needs a delete branch in `Indexer.delete` and a line in `deleteActor`.
- **Recordings (`feed.activity#recordingOf`) are honored only within one author's repo.** The indexer stores `recording_of` only for a link to another of the author's own activities. `shownInFeeds` (`api/Views.kt`) hides a recording from feeds only while the activity it names is indexed and isn't itself a recording, and `hydrate` lists a primary's `recordings`. Queries that look for duplicates (`getAuthorActivitiesByStart`) return recordings too.
- **The AppView syncs athletes' tier spaces as a member** (`sync/SpaceSyncer.kt`), with its own identity: `APPVIEW_SIGNING_KEY` (P-256, hex; `scripts/dev.sh` generates it into `docker/.env`, the Gradle `run` task reads it) is published as `#atproto` in `did.json` and signs the delegation tokens `SpaceCredentials` exchanges (`SignedDelegationTokens`). Without the key nothing is synced and only public activities exist. Clients announce a space with `notifySpace` (service auth from its authority; only `followers`, `mutuals`, `self` and `interactions`); the syncer joins it, registers for `notifyWrite` at `<serviceDid>#activitytracker_space_syncer` (its own audience, so AppView and managing-app tokens never work there), backfills (head revision from `listRepoOps`, then `listRecords`, since the op log may be compacted) and then pulls ops after the last indexed revision. A space that hasn't synced for an hour (backoff, downtime) is backfilled again instead, dropping indexed records it no longer lists, since the ops it missed may be compacted away. The authority's PDS sends each notification once, so every space is also pulled every 15 minutes and its registration renewed 2 h before expiry. A failing space backs off on its own; `SpaceDeleted` drops it and its rows. A PDS caches DID documents, so a new or rotated key is picked up only on a later retry.
- **Activity photos (`feed.activity#media`).** `boundedPhotos` keeps the `#image` members whose blob is WebP or JPEG, within the lexicon's size, with a real CID (other union members stay in the repo but not the index), and `activity_media` lists them. On a public activity, `GET /img/media/{did}/{cid}` (`api/BlobRedirects.kt`) redirects to the PDS's `sync.getBlob`, like the avatar route. A non-public activity's photo URL is signed for the viewer the view was built for (`PrivateMediaTokens`, since image loaders send no service auth); the route checks the signature, re-checks `visibleTo`, fetches the blob from the space as a member (`SpaceBlobs`, which keeps recent blobs in memory by CID) and answers `Cache-Control: private`, never redirecting.
- **Don't trust client timestamps for ordering.** Feed order uses `sort_at = min(createdAt, indexedAt)`, so a client can't pin a record to the top by dating it in the future.
- **Migrations.** These are Flyway files in `src/main/resources/db/migration`, named `V<n>__<description>.sql`. Never edit a migration that is already committed. Add the next `V<n+1>`, because the local Postgres has already applied the old one and Flyway rejects a changed checksum. Keep SQL portable: tests run it on H2 in `MODE=PostgreSQL`, so use no Postgres-only types or functions. Timestamps are `BIGINT` epoch millis. SQL that only PostgreSQL can run (extensions, GIN/trigram indexes) goes in `db/vendor/postgresql`, which `DatabaseFactory.migrate` adds for that database only. Its versions share one sequence with `db/migration` (`MigrationVersionsTest` checks).
- **Routes.** Add queries with `xrpcQuery(X.method, verifier) { params, viewer -> ... }` in `Routes.kt`. Auth is optional at that level. The only procedures are the sync callouts (`notifySpace`, `notifyWrite`, in `spaceSyncRoutes` via `xrpcProcedure`): clients write records to their own repos and spaces, never through the AppView. A handler that needs a viewer throws `AuthException`. Map client errors to `XrpcError(status, "ErrorName", message)`.
- **Tests** (`AppViewTest`) feed `JetstreamEvent.Commit`s into a real `Indexer` over H2 and then read back through `testApplication`. Test new indexing and views the same way, end to end.
