# Theme, adaptive components and navigation shell

Each platform follows its own conventions in one shared UI. The design system (`ui/theme`, `ui/adaptive`, `ui/chart`) lives in `:ui-designsystem` (`ui/designsystem`); domain composables like `MediaRow` and `ActivityDetailsForm` in `:app-common-ui` (`app/common/ui`); both keep the `app.ui` packages. `ui/theme` has the brand (teal, amber `tertiary` for likes) as full Material 3 schemes. `AppTheme` adapts it by `LocalUiPlatform`: Material 3 on Android; iOS grouped surfaces, Apple text styles and dimming instead of ripples on iOS; Inter (bundled in `:ui-resources`' `nonMobileMain/composeResources`) and a denser scale on desktop and web. UIKit colours with no Material role (`tertiarySystemFill`, the segment thumb) are `IosColors`, read through `LocalIosColors`; add to it rather than hard-coding a colour in a wrapper.

Screens build from `ui/adaptive` (`AppScaffold`, `AppTopBar` (a `titleMenu` makes its title a picker, like the feed's scope), `AppButton`/`AppSecondaryButton`/`AppTextButton`/`AppIconButton`, `AppTextField`, `AppSegmentedControl`, `AppSwitch`, `AppCheckbox` (`AppTriStateCheckbox` for a partly selected group; expect/actual, a native `UIImageView` with SF Symbols on iOS; content pinned over a scrolling list, like a sticky header, provides `LocalPinnedOverContent` so its marks go over the Compose canvas and rows can't show through), `AppFilterChip`, `AppRangeSlider` (two thumbs choosing a range, Material's everywhere since UIKit has none), `AppCard` (a group of content, like a metric's card: an outlined Material surface, or on iOS an inset grouped section on the grouped background), `AppListSection` and `AppListRow` (a titled group of rows, like Settings': Material list items under a coloured heading, or on iOS an inset grouped cell with hairlines between rows; a row has a title, an optional summary of its value, a chevron when it opens something or a trailing control, and a selected state for the row whose page shows beside the list), `AppMenu`, `AppBottomSheet` (with `AppSheetHeader`), `AppDatePickerDialog`, `AppAlertDialog`, `PlatformIcon`, `ReadableList`, `WithWindowWidth`), never the Material widgets those wrap; detekt's `UseAdaptiveComponents` enforces this. A wrapper that differs by platform is `expect`/`actual`, like `AppCheckbox`: the iOS look in `iosMain` (`Foo.ios.kt`), Material in `nonAppleMain` (`Foo.nonApple.kt`), so neither compiles into the other's build. `AppSegmentedControl` (`UISegmentedControl`) and `AppProgressIndicator` (`UIActivityIndicatorView`, also `AppPullToRefresh`'s iOS spinner, faded on the view since a `graphicsLayer` alpha can't reach it) are native `UIKitView`s; the rest of the iOS actuals are drawn in Compose. Wrappers that only forward to Calf (`calf-ui`) stay in commonMain, since Calf already picks UIKit's native piece: menus, sheets, switches, alerts (`AppAlertDialog` takes any number of actions, through Calf's `AdaptiveBasicAlertDialog`) and the tab bar; `AppDatePickerDialog`'s iOS actual uses Calf's date wheels. A native view normally sits under the Compose canvas and shows through a cut-out, which exposes the window's white behind any translucent part or Compose fill. Both native wrappers therefore set `placedAsOverlay`, which means they draw above Compose content that scrolls over them, including the top bar, whose blur can't reach them. So a native view over the canvas hides itself under its `AppScaffold`'s iOS top bar with `rememberUnderTopBar()` (`UnderTopBar.ios.kt`): it puts the helper's `modifier` on its `UIKitView` and calls `update(view)` from the update block, which masks the view out across the bar's edge as the bar reads `TopBarEdge`, and one that takes touches gives its `UIKitView` no `interactionMode` while `covered`, since Compose's interop wrapper otherwise takes the bar's taps.

Screens lay out by window width, never by platform: `WithWindowWidth` (a `BoxWithConstraints` at the screen root) gives a `WindowWidth` of `Compact` (under 600dp: one column, any phone or a narrow desktop or web window), `Medium` (to 840dp: two columns) or `Expanded` (a side pane beside the content). Platform look stays in the wrappers above.

The iOS navigation bar is drawn in Compose, because Calf's native one is pinned to the window and can't follow screen transitions or swipe-back. It is clear at rest and blurs the content scrolled under it with Haze (`AppScaffold` makes the content its source): iOS 26's soft scroll edge effect, or a material and hairline before iOS 26 (`usesLiquidGlass`).

Signed in on Android, desktop and web, `nav/AppShell` wraps the navigable screens: a bottom bar or rail on Android, and a sidebar on wide desktop and web windows. On iOS the app's shell is SwiftUI (`iosApp/iosApp/Shell`, ui/ios-native-shell): `RootView` follows the presenter host (`:app-host`) between sign-in and a session, and `SessionView` shows the system's `TabView` with a `NavigationStack` per tab whose path follows that tab's Kotlin stack. A screen with an entry in `ScreenRegistry` is a SwiftUI view; every other screen is `FallbackScreen`, one Compose view controller per screen drawing the screen's shared UI from the states the host publishes, with the Compose navigation bar described above and its content scrolling under the system's tab bar, which is in its safe area. `AppShell`'s iOS branch (Calf's tab bar) and the gesture navigation decoration no longer run on iOS, where going back is UIKit's pop and `BackSwipe` keeps the edge swipe working on screens whose native bar is hidden; both leave with Compose there. Each `TopLevelDestination` keeps its own back stack (`resetRoot` with save/restore). `App` tells each screen through `LocalIsNavRoot` whether it is a tab root, which drops its back button and gives it a large title on iOS.

A native iOS screen builds from the Swift design system in `iosApp/iosApp/Design` (ui/ios-design-system), which holds only what the system doesn't already give: the theme's colours as catalog colours (`AccentColor`, `OnAccentColor` for a label on the accent fill, `LikeColor`; everything else is the system's palette), `AppButton`/`AppSecondaryButton`/`AppTextButton`/`AppIconButton`, `AppTextField`, `AppListRow` (for the system's `List` and `Section`, which draw the grouped look; `selected` marks the row whose page shows beside the list), `AppCard`, `AppProgress`, `Image(AppIcon)` and `SportIcon` over the generated symbols and images, `ErrorMessage`, and `ContentStateView`/`RefreshStatusView` for ui/content-loading. There is no Swift wrapper for a sheet, menu, alert, date picker, toggle, segmented picker or pull to refresh: SwiftUI's are the platform's. Each piece is in `Previews/DesignGallery.swift` and has reference snapshots.

Settings is a list beside a detail pane when the window has room (ui/settings-layout): once the content is `Expanded`, from 840dp, on Android, desktop and web, and on iOS in a window at least 700 points wide and 500 tall (`settingsSplitFits` in `:app-host`), which is every iPad at full screen either way up and never an iPhone. Off iOS, `nav/SettingsListDetailDecoration` wraps the gesture navigation decoration in `App`: when the stack ends in `SettingsScreen` with only `SettingsPage`s above it (`:app-common-api`; settings' own pages, the gear list and the block lists carry it), it hands the delegate the stack trimmed to Settings and draws Material 3 adaptive's `ListDetailPaneScaffold` (JetBrains' `adaptive-layout`, never `adaptive-navigation`) in Settings' slot: the list, and the top record beside it, or `ActivityDefaultsScreen` as plain `CircuitContent` while nothing is open. Anything else on top, or a narrower window, passes through untouched. The back stack stays the only selection state: rows `popUntil { it is SettingsScreen }` then `goTo`, so a page replaces the open one, and Settings' own back does `popUntil` then `pop`, so it leaves with the page beside it. Each record is a per-key `movableContentOf`, so crossing the breakpoint moves compositions rather than rebuilding them, and both panes run under `ProvideRecordLifecycle(isActive = true)`. It provides `LocalSettingsPane` (the list marks the shown row) and `LocalIsPaneRoot` (`ui/adaptive`; the pane's first page drops its back button but, unlike `LocalIsNavRoot`, gets no large title). A new settings page implements `SettingsPage`; previews and screenshots lay it out with `SettingsListDetailPreview`.

The iOS app turns with the device (portrait and both landscapes on iPhone, all four on iPad; `INFOPLIST_KEY_UISupportedInterfaceOrientations_iPhone` and `_iPad` in the Xcode project), so a screen never assumes which way up it is: it lays out by the size it gets. On iOS the same layout is the SwiftUI shell's, decided by the presenter host (`compose-screens.md`): `StackView` reports its size (`TabStack.setSize`), pushes `shown.pushed`, and gives the record that has a `paneDefault` (Settings) the destination `SettingsColumns`, which draws the native list and, while `shown.split` is set, the split's page in a second column 360 points from the leading edge. The list is the same view narrow and wide, so it keeps its scroll position across the width. The bar over both columns is the tab's stack's own, with the system's back button and edge swipe, which pop Settings and the pages Kotlin holds above it together; `SettingsEvent.Back` is never sent there. A page in the column is whatever draws that record, today always the shared UI's `FallbackScreen` (`ScreenView(inPane:)` leaves the stack's bar alone), which hides its back button under `LocalIsPaneRoot` from `HostRecord.paneRoot`. `SettingsView` marks a row by asking Kotlin's `SettingsPane.marks`, as `SettingsUi` does. The app declares portrait only, so an iPad narrower than 840 points upright (an 11-inch one is 834) stays one page at a time.

Activity media show through `ui/MediaRow` (the route map, then each photo, in one sideways row, on the feed card and the detail page) and the full-screen `MediaGalleryScreen` (a `HorizontalPager`; tapping a photo zooms it with ZoomImage's `CoilZoomAsyncImage`). Images load with Coil; `App` sets the singleton loader up with `HeldPhotoFetcher`, which serves `heldphoto:` URLs from the signed-in session's uploaded bytes (`HeldPhotos`). The import and edit screens share `ui/ActivityDetailsForm` (title, description, dive site, photos), which compresses each picked photo with `compressPhoto` (WebP through Skia on iOS, desktop and web, `Bitmap` on Android) before it reaches the presenter.

Charts are built on Vico (`com.patrykandpatrick.vico:multiplatform`, every client target) with the shared pieces in `ui/chart`: `StaticChart` (fitted to its width, no scroll, zoom or animation, with a content description), `chartColors` from the theme, `StepConnector`, `WholeRangeXStep` for charts without an x axis, `PointLabels` for value labels kept inside the chart (Vico's own data labels shrink between close points and skip the ends), `TimeSeriesChart` for a value over an activity with y and time axes, and `ZoneBars` for time in zone (plain rows, so each reads as one sentence to a screen reader). Build new charts from these rather than drawing on `Canvas`.
