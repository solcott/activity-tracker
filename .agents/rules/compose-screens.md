# Screens, Circuit and Metro

Use the `new-screen` skill to scaffold a screen. The rules it follows:

- A screen is a `@CircuitSerializable(<scope>::class) data object/class XScreen : Screen`, plus an `XState : CircuitUiState` with an `eventSink`, an `XEvent` sealed interface, a presenter and a UI. Screen args must be serializable: pass IDs and AT-URI strings, not views.
- Use the same scope in `@CircuitSerializable` and both `@CircuitInject`s. `SessionScope` is for signed-in screens. `AppScope` is only for signed-out ones such as login. A mismatched or missing registration compiles fine but crashes at runtime the first time navigation state is saved.
- The presenter is a `@CircuitInject(XScreen::class, <scope>::class) @Composable fun XPresenter(screen, navigator, ...deps): XState`. Circuit supplies `screen`/`navigator`, and Metro injects the rest. Don't write a presenter class with `@AssistedInject`. A class with plain `@Inject` is fine only when it needs neither screen nor navigator (like `LoginPresenter`).
- The UI is `@CircuitInject(XScreen::class, <scope>::class) @Composable fun XUi(state: XState, modifier: Modifier = Modifier)`.
- **One screen spans three modules, all in the same feature package `io.github.solcott.activitytracker.app.<pkg>`:** `XScreen.kt` (Screen, State, Event) in `feature/<pkg>/api`, `XPresenter.kt` in `feature/<pkg>/presenter`, and `XUi.kt` in `feature/<pkg>/ui`, each module's script only `plugins { id("activitytracker.feature.api|presenter|ui") }` plus any other feature's `-api` it opens. Presenters and UIs see each other only through the contracts. Presenter modules have the Compose runtime and foundation, but only for `TextFieldState`: no material3 and no UI code (layouts, modifiers, emitting composables). `composeApp`, `webApp` and `desktopApp` depend on presenter and UI modules only so their graphs aggregate the factories; a new feature's `-presenter` and `-ui` join their dependencies. Never import a presenter from UI code; `checkModuleBoundaries` fails a presenter module depending on a UI module (or the reverse) and a feature depending on another's presenter or UI module (dev/module-boundaries).
- **Shared code has one home.** Whatever two features use goes to the shared module for its layer, never a copy: contracts (`UiError`, visibility, route and details-form types) to `app/common/api`, presenter helpers (`rememberSingleFlight`, `DetailsForm`, `uiErrorOf`, `rememberReporting`, …) to `app/common/presenter`, domain composables (`ActivityCard`, `ActivityMap`, `VisibilityPicker`, `startTime`, …) to `app/common/ui`, design-system pieces with no app types (`ui/adaptive`, theme, charts, `TestTags`) to `ui/designsystem`. Same package as before; make a moved `internal` public. `ActivityTypePicker` and `expect` UI helpers (`LocationPermission`) stay in `composeApp` until record moves.
- **Text fields** take a `TextFieldState`, never the `value` + `onValueChange` overloads (`String` or `TextFieldValue`). It is the app's own type (`:core-textfield`, package `textfield`), imported with its `rememberTextFieldState`, `setTextAndPlaceCursorAtEnd` and `clearText` from there and never from Compose: off iOS it is Compose's class under the same name, and on iOS a class Swift export can carry (dev/ios-swift-interop). Compose's import compiles everywhere but iOS, so detekt's `UseAppTextFieldState` refuses it outside `*Test.kt` files. Outside composition (a `State`'s default, a sample) make one with `textFieldStateOf("text")`, since the type has no constructor in common code. When the presenter needs the text (to save, validate or search), it owns the state: `rememberTextFieldState()` in the presenter, a `TextFieldState` field in `State`, no `XChanged(String)` event. The presenter reads `.text` when it acts, fills a loaded value with `setTextAndPlaceCursorAtEnd` and empties it with `clearText`; tests, which run on the JVM, edit the state the same way or with Compose's `edit { }`. Reading `.text` in a `State` getter (`valid`) or in the presenter's composition keeps it live. A native view redraws only on a new state, so a getter a native control follows (Send's `canSend`) also needs the presenter to read the `.text` in its composition, into a field of the state (`ReportState.noteWritten`), or typing publishes nothing. Text only the UI uses (a picker's search box) is a `rememberTextFieldState()` in the UI. A `readOnly` field showing a value takes `rememberReadOnlyTextFieldState(text)` (`ui/`). Use `lineLimits = TextFieldLineLimits.SingleLine` and `onKeyboardAction`, not `singleLine`/`keyboardActions`, and an `InputTransformation` to react only to typing (opening a menu). detekt's `UseTextFieldState` rule (`:detekt-rules`) enforces this; it can't see types, so name every argument after the state.
- **Platform look.** Build UIs from `ui/adaptive` (`AppScaffold`, `AppTopBar(title, onBack = ...)`, `AppButton`, `AppTextField`, `AppMenu`, `AppIconButton(AppIcon.X, ...)`…), not Material's `Scaffold`, `TopAppBar`, buttons, text fields, progress indicators, sheets or dialogs; detekt's `UseAdaptiveComponents` flags those. Give a screen `onBack` even if it can be a tab root: `AppTopBar` hides the button at the root (`LocalIsNavRoot`). Lists go in `ReadableList` (centred column and scrollbar on desktop and web), and scrolling forms take `Modifier.readableWidth()` inside a `ScrollbarBox`. Pass `AppScaffold`'s padding to them as content padding (`ReadableList(contentPadding = padding)`, or `.padding(padding)` after `verticalScroll`), never as a `Modifier.padding` around the scroll, so content scrolls under the bars. A scrolling screen also gives its bar a `rememberAppTopBarScrollBehavior()` and puts its `nestedScrollConnection` on the `AppScaffold` (on the list, inside pull to refresh): the bar then marks content scrolled under it, and a tab root's large title collapses on iOS. A screen that is one list does all of this with `ListScreen` (`:app-common-ui`), taking its items as a `LazyListScope` builder, with a `ContentState` overload that adds `ContentStateLayout`. Branch on `LocalUiPlatform` only for real differences in behaviour, like pull to refresh on phones or Android's Record FAB. A new full-screen flow also joins `TopLevelDestination.FullScreenFlows`.
- **Text.** Every string a UI shows (labels, content descriptions, units, counts) lives in `ui/resources/src/commonMain/composeResources/values/strings.xml` (`:ui-resources`, which every UI module and app shell depends on) and is read with `stringResource`/`pluralStringResource` from the generated `io.github.solcott.activitytracker.composeApp.resources.Res` (the package it kept when it moved out of `composeApp`). Use `<plurals>` for counts. Shared helpers: `sportLabel`/`activityTypeLabel` (looked up by token as `sport_<token>`/`sub_sport_<sport>_<token>`), `handleLabel` (`ui/Labels.kt`) and the composable unit formatters in `Format`. What each of those says is chosen in `:app-common-api` as an `AppText` and only resolved here (below). Presenters can't read resources, so a failure goes in `State` as a `UiError` (`:app-common-api`), never a `String`: `UiError.of(kind, cause)` keeps what failed and why (`reason`, a `DataError` from `toDataError`), never the exception's message. Add a `UiError.Kind` and its string, and the UI shows it with `errorText`, the one renderer for every error (ui/error-messages): the kind's text, plus unreachable, server or unreadable when the reason is one of those.
- Metro generates the Circuit factories (`metro.enableCircuitCodegen=true`). There is no Circuit KSP processor, so don't add one.
- **Shared pieces of a screen.** Presentation logic that several screens repeat lives in one owner, so a host only places its state:
  - **A sub-state with its own sink.** A field of `State` (`@Immutable`, in the `-api` or `:app-common-api`) carries an `eventSink` for its own event, and the holder that owns it fills the sink with `::onEvent`: `ActivityDetailsFields` (`DetailsForm`), `VisibilityFields` (`NewActivityVisibility`, `EditVisibility`, `DefaultVisibilitySettings`), `ActivityTypeField` (`ActivityTypeChoice`) and `PlaceNameFields` (`rememberPlaceNames`, a segment's or dive site's names). The host declares no event and adds no `when` branch; the shared UI sends to `fields.eventSink`. Default the sink to `{}` so a `State` default can be built.
  - **A host-wrapped shared event** when handling it needs the host's `Navigator`: `ActivityListEvent`, wrapped as `FeedEvent.Activity(...)` and handled by `rememberActivityListEventSink(navigator, activities, onError)`.
  - **Producers.** Most are a `@Stable` holder plus a `@Composable rememberX(...)` that takes its repositories as arguments (`rememberNewActivityVisibility`, `rememberApprovesFollowers`). When a producer would only pass a repository through, make it an unscoped `@Inject` class with a `@Composable produce(...)` that Metro injects into the presenter instead (`ActivityTypeChoices`).
  - **Cursor lists** use `rememberRetainedPaging(key, idOf = …, onKeyChange, enabled, initial) { cursor -> flow { emit(repo.xPage(cursor)) } }` (`uistate-circuit`, ui/content-loading) over a repository's `Outcome<Page<T, M>>` read, and put its `PagedState` in `State` whole. It keeps the items through a failed refresh or page, retries only what failed, shows the pages at once on return, and de-duplicates by id. A new key keeps the old items until it answers (`KeepItems`, search) or clears them. The host edits the items with `update {}` after a write and keeps an action's failure in its own `UiError`, never in the load's status. The UI lays the list out with `LoadMoreAtEnd`, `pagedRefreshStatus` and `pagedFooter` (`ui/PagedList.kt`), which say why through `errorText`. A nested list (a thread's replies) gets one holder per parent inside `key(parent.id)`, seeded with `initial`.
  - **Choose a SubCircuit instead** only when the child needs nothing pushed from the host after it's created: a SubCircuit sees the host only through its screen, and a new screen remounts it. The type picker isn't one because import sets the type from the file.
- **Sub-screens (SubCircuit).** For a reusable piece of a screen with its own presenter and UI (a filter bar, a picker), use `circuitx-subcircuit`, not a screen or a plain composable. It is opted in module-wide (`ExperimentalSubCircuitApi`). The session's `SubCircuit` is built from Metro-multibound `SubPresenterFactory`/`SubUiFactory` sets (`CircuitBindings.kt`) and provided as `LocalSubCircuit` in `App.kt`. There's no `AppScope` one yet. It spans the same three modules and package as a screen:
  - **Contract** (the feature's `-api`): an `@Immutable` `XScreen : SubScreen<XOuterEvent>`, an `XState : SubCircuitUiState` with an `eventSink`, an `XEvent` and an `XOuterEvent : SubCircuitOuterEvent` sealed interface. The screen carries only initial config, never live state: `SubCircuitContent` remembers the presenter per screen and keys its content on it, so a changed screen remounts the child and drops its state.
  - **Presenter** (the feature's `-presenter`): a `@SubCircuitInject(XScreen::class, <scope>::class) @Inject class XPresenter(screen: XScreen, ...deps) : SubPresenter<XOuterEvent, XState>`, a class because SubCircuit has no function form. Metro injects the screen (leave it out if unused); no `@AssistedInject`. There's no navigator. It seeds its state from the screen (`rememberRetained { mutableStateOf(screen.initial) }`) and reports it with a keyed `SideEffect(value) { outerEventSink(...) }`, which also fires when first shown, so the host matches it even after one side lost its state.
  - **UI** (the feature's `-ui`, or `composeApp`): a `@SubCircuitInject(XScreen::class, <scope>::class) @Composable fun XUi(state: XState, modifier: Modifier = Modifier)`, the same function form as a screen's UI. `SessionPreviewSubUis` (`composeApp`, the module that sees every feature UI) registers it for `AppPreview` with `SubUi<XState> { state, modifier -> XUi(state, modifier) }`.
  - **Host**: `SubCircuitContent(state.xScreen, outerEventSink = { state.eventSink(Event.XChanged(it...)) })` in the UI. The host presenter creates the screen once (`rememberRetained { XScreen(initial) }`) and keeps what it needs from outer events in its own state; it replaces the screen only to reset the child. Parent and child talk only through the screen (down) and outer events (up).
  - **On iOS** a native view draws a sub-screen through the presenter host: `SubScreenView(record, screen: state.xScreen, outerEvent: { … }) { (state: XState) in XView(state: state) }` (`Shell/`), which asks the record for it (`HostRecord.sub`) and maps outer events (cast to the contract's types) to the screen's events as the Compose UI does. A sheet that stops drawing its sub-screen while the screen still shows closes it (`HostSubRecord.close()`), or an equal sheet reopens with the old state. `FeedFilterBar` is the first. A sheet sub-screen is SwiftUI's own `.sheet`, shown from its carrier by a view modifier (`reporting(_:)` for `Reporting`, `placeNames(_:)` for `PlaceNameFields`): it reads the page's record from the environment (`\.hostRecord`, set by `NativeScreen`; nil in previews and snapshots, where it shows nothing), keeps the screen it opened with while the sheet slides away, sends the carrier's own close on a swipe down, closes the sub-record in `onDismiss`, and shows the carrier's alert (Block, delete) only once the sheet has gone. A page with `Reporting` adds `.reporting(state.reporting)` and sends a `ReportingEvent.Open` Kotlin builds (`ProfileState.reportEvent`), so Swift never builds a `ReportTarget`.
  - **Tests**: `circuitx-subcircuit-test`'s `presenter.test { awaitItem(); outerEvents.awaitEvent() }` in the presenter module's `src/jvmTest`.
- **Event-driven work goes through `rememberSingleFlight()`** (`:app-common-presenter`), never a bare `rememberCoroutineScope()`: `flights.launch(key) { ... }` drops a repeat while the first runs, so a double tap can't save, follow or like twice. The key is the event (`XEvent.Save`, `XEvent.Changed::class` for one with args) or what it acts on (an activity's URI for its like). Derive a `saving`/pending flag from `flights.isRunning(key)` instead of a separate `var`, and use `launchLatest` only when a newer request should replace the running one (a new file pick). detekt's `UseSingleFlight` rule flags `rememberCoroutineScope()` in `*Presenter.kt`. A presenter test for a write sends the event twice while the first is in flight (gate the fake's response) and asserts one write (`ProfilePresenterTest`). A flight is cancelled when the screen leaves: work that must outlive the screen (a batch import's save) is persisted and run app-wide instead (`ImportSaveStore`, `ImportSaves`; data-and-auth), the presenter following it by id.
- **Loaded content is a `ContentState`** (`io.github.solcott:uistate`, ui/content-loading). The presenter collects the repository's `Flow<Outcome<T>>` with `produceRetainedContentState(initial, retryKey) { … }` (`uistate-circuit`), or `produceRetainedContentStates(contentStatesOf(…), retryKey) { combineOutcomes(…) }` for several sources (`SegmentPresenter`), and puts it in `State` whole; a Retry or Refresh event bumps the key, which restarts the stream under the same state, so content stays on screen. Key it with `key(…)` instead when a new parameter must not show the old one's content (`FeedPresenter`'s filter). Retained, it shows at once when the athlete comes back. The UI draws it with `ContentStateLayout(state.content, UiError.Kind.LoadX, onRetry)` (first-load spinner or failure) and a `RefreshStatus` item over loaded content, which say why through `errorText`. Check `hasLoaded`, never emptiness or null, for whether anything has loaded. `UiError` stays for actions.
- Wrap suspend calls in `runSuspendCatching`, not `runCatching`, so cancellation propagates. Writes go through repositories (`ActivityRepository` → outbox), never straight to XRPC from a presenter.
- **Graphs.** `AppScope` is app-wide. `SessionScope` is the `SessionGraph` extension created per signed-in account (`key(did)` in `App.kt`). The concrete `@DependencyGraph`s are `AndroidAppGraph`/`IosAppGraph` in `composeApp` platform source sets and `WebAppGraph` in `webApp`. A module that declares a graph needs every contributing module (including `:app-common-presenter` and each feature's `-presenter` and `-ui`) on its compile classpath. `androidApp` can't use Metro intrinsics; it calls `createAndroidAppGraph` from `composeApp`.
- **The presenter host** (`:app-host`, dev/presenter-host) runs presenters with no UI, for a shell that draws their states natively. `AppHost` follows the signed-in account (`RootState`: restoring, signed out with the sign-in record, signed in with a `SessionHost`); `SessionHost` has a `TabStack` per `TopLevelDestination`, which is the `Navigator` that tab's presenters get, and the single records a leave shows; each `HostRecord` publishes its screen's `state`. One Molecule composition per scope runs the top record of the chosen tab and any record the UI reports visible, and keeps each record's `rememberRetained` and `rememberSaveable` state while it is in its stack, as `NavigableCircuitContent` does. So a presenter must keep working without a UI around it: read no composition local, and navigate only through its `Navigator` (`goTo`, `pop`, `popUntil`; `resetRoot` replaces the tab's stack, and nothing passes a pop result). What a signed-in session shows and when its background work runs is `SessionRunner`, which `App` and the host both run: add session-long work to `RepositorySessionSteps.runWork`, never to a `LaunchedEffect` in `App.kt`. The host's graph accessors (`AppGraph.appHost`, `SessionGraph.sessionHost`) are unused by the Compose shell. It also runs sub-screens (SubCircuits): a UI asks a record for the sub-screen its state embeds (`HostRecord.sub(screen, outerEventSink)`, the screen as `Any` since Swift has no `SubScreen` type), and gets a `HostSubRecord` publishing its `state`; the presenter comes from the session's `SubPresenterFactory` set and runs inside its record's composition, so its state is kept and dropped with the record's, and an unequal screen of the same class or `close()` starts it afresh. Its tests use fake presenters (`HostTesting.kt`, with `FakeSubPresenters`); `composeApp`'s `LoginThroughHostTest`, `FeedFilterThroughHostTest` and `ReportThroughHostTest` run real ones through it (`appHostOf`, `sessionHostOf`). The host also decides when Settings shows beside its page (ui/settings-layout): a UI reports its stack's size in points (`TabStack.setSize`), and with room for two panes (`settingsSplitFits`: 700 wide, 500 tall) `TabStack.shown` carries a `SettingsSplit` while the top of the stack is Settings and its `SettingsPage`s (`settingsPagesOnTop`, the rule the Compose decoration asks too). `shown.pushed` is then the stack up to Settings, and the split names the page to draw beside it: the top settings page, or Settings' `paneDefault`, an Activity defaults record that is never on the stack, runs only while reported visible, and lives as long as its Settings record. `HostRecord.paneRoot` tells the pane's first page it has no way back. The stack itself never changes with the width.
- **iOS draws every screen with no step, and a native view is opt-in** (ui/ios-native-shell). The SwiftUI shell (`iosApp/iosApp/Shell`) shows each of the host's records through `ScreenView`: a screen with an entry in `ScreenRegistry.app` is a SwiftUI view, and every other screen is `FallbackScreen`, the screen's own Compose `Ui` in a view controller. So a new screen needs nothing on iOS. A native view is `FooView(state: FooState)` in `iosApp/iosApp/Screens/` plus `registry.register(FooScreen.self, FooState.self) { FooView(state: $0) }`; the registry finds a screen by its class name (`HostRecord.screenName`), and naming the two types in Swift is also what links their generated modules into the app, so alias them in `Kotlin/KotlinTypes.swift`. It reads the state's fields, sends events to `state.eventSink` (`FooEvent.Save.shared` for an object, the class's initialiser otherwise) and switches over a sealed type with `sealedType()`. `LoginView` is the model for a screen on its own and `SettingsView` for one in a tab's stack: it sets `.navigationTitle` and uses the stack's own bar and back button, and never holds a navigation container of its own (a `NavigationStack` inside a stack's destination is never shown). A settings page (`ActivityDefaultsView`, `SegmentsAndGroupsView`, `PrivacyZonesView`, `Form`s; `GearListView`, `BlockListView`, `AccountView`, `LeaveView`, `TrainingZonesView`, inset grouped `List`s; the default and a sport's zones, `ZonesView` and `SportZonesView`, `Form`s with Save in the bar, the column's second page beside the list) sets `pageTitle(_:)` instead, and so does a page they open full width over Settings (`GearCollectionView`, `IgnoredSensorsView`, and the gear and collection forms `EditGearView` and `EditGearCollectionView`, `Form`s with Save as the page's bar action and a failed save in a row at the top) and a page pushed over a shared one (`FollowListView`, `FollowRequestsView` and `ActivityInvitesView`, over the profile, and `AddPeopleView`, over the activity, and `UploadsView`, over the feed, and `StarredSegmentsView`, over the profile, and the boards `SegmentLeaderboardView`, `SegmentMayorsView` and `DiveSiteRegularsView`, over the segment and dive site pages, and `EditProfileView`, a `Form` over the profile with Save in the bar and the shared sign-in-again notice at the top; and `ImportBatchView`, over the feed, the first page drawn with the native activity card, and `ProfilePage`, the profile in the You tab's stack (named so because `ProfileView` is the lexicon's alias), whose menu's Report opens the native report sheet and whose Posts tab draws native post cards; `pageTitle(_:subtitle:)` puts whose list it is under the title): the stack's bar when it is alone, and a column header (`PageBar`) when it shows beside Settings' list, where a page's navigation title never shows (`ScreenView(inPane:)` sets `\.inPane`, and `\.paneRoot` from `HostRecord.paneRoot`). A page that can be opened deeper than the column's first passes its own way back (`pageTitle(_:back:)`, sending its `Back` event, as Leave does from Account), which the header shows as a back button there; `canGoBack: false` hides every back button, the stack's and its edge swipe too, as a running leave does. A row's control stays on one line at the trailing edge and a long label wraps beside it: the form's own `Picker` row puts the choice under a label that doesn't fit, so a menu choice is `AppPickerRow`, a `Menu` holding an inline `Picker` (Activity defaults' row, moved into the design system), which also keeps the form's row height. A sheet that needs a bar holds a `NavigationStack` of its own, which shows (unlike one inside a stack's destination); a reorderable section sits in a `Form` held in edit mode (`EditGearCollectionView`), SwiftUI's move offset turned into Kotlin's final index by `MemberMove`, with the shared move and remove labels as accessibility actions. A photo is picked with `PhotosPicker` in its compatible encoding and handed as bytes to `IosApp.compressPhoto`, the shared `compressPhoto`, through `PhotoPick`, which retries a picture Skia can't read (a HEIC) as UIKit's JPEG, and sends the result in the screen's own event (`EditGearEvent.PhotoPicked`); `PhotoPickOf<Photo>` is generic over what Kotlin's compression gives, so edit profile's `AvatarPick` hands the bytes to `IosApp.compressAvatar` (the shared `compressAvatar` in `:app-common-ui` beside `compressPhoto`, a 512 px JPEG, since the shell reaches a feature only through its `-api`) and sends `AvatarPicked`. A field limit the shared form only counts (a red counter and Save held back) gets no refusing `TextFieldRules` natively either: a refusal also refuses shortening a value already too long. A `LocalDate` reads as `year`, `month` (a Swift enum whose `rawValue` is its ordinal) and `day`, and is built with `LocalDate(year:month:day:)`; `CalendarDay` turns it into the start of that day in the device's calendar for a `DatePicker` and back; a date a contract holds as `YYYY-MM-DD` text gets a `LocalDate?` getter and an event constructor taking one (`EditProfileState.birthDay`, `BirthDateChanged(date:)`), so Swift never parses or formats it. A `TextFieldModel` follows its `TextFieldState` only while its `AppTextField` is on screen, so a condition that decides whether a field shows reads the Kotlin state (`state.gender.value`), never the model of a field that is hidden. Swift export silently leaves out a member named `description` (every Swift object has one), so such a field gets a getter under another name (`EditProfileState.bio`, and `ProfileState.bio` for the lexicon's `ProfileView.description`); read the generated Swift for a new contract's fields. An activity in a list is `ActivityCardView(content:)` (`Screens/ActivityCardView.swift`), a list row in a section of its own, drawn from Kotlin's `ActivityCardContent` (`:app-common-api`, which the shared `ActivityCard` asks too: who and when, the labels' notices and blur, the title, `stats(units)`, the owner's `locks()`, the media and `routeShape`, `offersLike` and `liked`); it sends the shared `ActivityListEvent`s, which the host wraps, and its route is `RouteSketch`, a `Canvas` stroking Kotlin's `RouteShape` (the served line placed on the tile by `TileFit`, the fit the shared `canvasFit` uses too, smoothed, with its breaks and markers), never a map. A post in a list is `PostCardView(content:)` (`Screens/PostCardView.swift`), drawn from Kotlin's `PostCardContent` (`:app-common-api`, `app.posts`, which the shared `PostCard` asks too), sending the shared `PostEvent`s the host wraps; a subject's comments are `CommentsSection(state:)` inside the page's `List`, its rows Kotlin's `CommentsTexts.rows` (the actions the shared list asks for each comment from `CommentsTexts.actions`); and a host's `QuoteFields` are drawn by `.quoteSheet(fields)`, a SwiftUI sheet and delete alert, since they are plain state, not a sub-screen (`PostPage`, `PostQuotesView`, the profile's `ProfilePosts`). A screen's first state can arrive after its view is made, which `Following` handles; a view that follows a flow by hand must not hang its task on content that can be empty. A `:core-data` model's plain `List` fields (`UploadQueueView`'s) read as typed arrays, empty ones too: only the immutable library's shared empty instance stops the app. A state's `ImmutableList` or `ImmutableSet` is read with `elements(as:)` (`Kotlin/KotlinCollections.swift`), which gives a typed array for text, whole numbers (`Int32`, `Int64`) and classes Swift has a type for; it can't carry a Kotlin enum (a choice among an enum's values, or the kinds a page shows, is an immutable list of a contract class holding the value as a property, which Swift reads as the enum: `GroupOption`, `ZoneKindOption` with the state's `offers(kind)` for both UIs to ask), and a class from `:core-data` or `:core-lexicon` that only ever appears as a collection's element has no Swift type until some exported signature names it (`ZoneTexts.label(zone)` and `privacyZoneName(zone, index)` name `Zone` and `PrivacyZone`). A sealed state of the contract or of `:core-data` (`GrantStatus`, `DataExportStatus`) casts with `as?`, and a `kotlin.time.Instant` reads as a class with `epochSeconds`, and a `kotlin.time.Duration` as a class with `inWholeSeconds`; a `Set` of enums stops the app like a list of them (`GrantStatus.Outdated.missing`), so a native view gets its members as text (`AccountTexts.missingFeatures`). A `suspend` function on `IosApp` is an `async throws` call Swift awaits (`IosApp.writeArchive`, which zips a data export to a file for the share sheet); a Kotlin class passed into one from the main actor is marked `nonisolated(unsafe)`, since Kotlin's classes aren't `Sendable` to Swift, and a `CharSequence` parameter doesn't take a Swift `String`, so a function Swift calls takes `String`. A `PagedState` or `ContentState` reaches Swift with its type parameters erased: `items` is an array to cast (`$0 as? BlockListAccount`), `data` a value to cast (never a list: through the erased `data` a list arrives as a Swift array and an empty one throws when read, so a `ContentState` of a list gets a typed getter on its state, `IgnoredSensorsState.sensors`, or a content holding lists whose shown one is a getter, `FollowRequestsState.accounts`, `ActivityInvitesState.invites`, `AddPeopleState.invitees` and `followers`, which the view reads with `elements(as:)` inside `ContentStateView`'s form without a value), and the library's extensions (`hasAnswer`, `hasLoaded`) aren't exported, so what they decide is a rule in `:app-common-api` (`PagedShown`, `ContentShown`). Don't add a `List` twin that returns the immutable list itself: the generated getter stops the app when that list is empty (return a copy, `toList()`, as `ThresholdHistorySection.shownRows` does even when it shows every row), and a `List` of enums stops it either way.
- **What a native view draws with** (dev/ios-native-resources, ui/ios-design-system). Strings are Xcode's symbols for the generated catalog: `Text(.loginIntro)`, `.loginLeft("alice.test")`, a plural as `.likeCount(quantity: 3, "3")`; every placeholder is a `String`, and a number goes in as text shared code formatted (`formatWhole`), never as an `Int` for Foundation to group. Never a string literal key, which compiles when the string is gone. Controls come from `iosApp/iosApp/Design`: `AppButton`, `AppSecondaryButton`, `AppTextButton`, `AppIconButton` (always with a label), `AppTextField` over the state's `TextFieldState` with a `TextFieldModel` the view holds (it shows what the presenter seeds or clears, takes digits-only and maximum-length rules (a digits-only field keeps an edit's digits and drops the rest; an edit over the length is refused whole), a `hint` shown while it is blank, and has supporting text and an error state; `layout: .row` puts it in a grouped form's row, label leading and text trailing, and `.multiline` under its label over several lines; its label is a catalog symbol or an `AppText`), `AppPickerRow` for a menu choice in a form, `AppListRow` in the system's `List` for a setting, `AppItemRow` for a thing in a list (a picture, a title with lines under it, a summary, and a trailing control that takes its own taps), `pageTitle` for a settings page (with `subtitle:` for a second line under the title, the system's navigation subtitle on iOS 26 and a two-line title before, and `actions:` for its bar's buttons, which go in the stack's bar alone and in the column header beside the list), `AppCard`, `AppProgress`, `Image(AppIcon)`, `SportIcon`, `ErrorMessage`, `ContentStateView` with `RefreshStatusView` for a `ContentState` (the value's type is named, since Swift export erases it), and `PagedList` for a `PagedState` (the item's type and id named; it asks for the next page once the last item is on screen, and lays out `PagedShown`, the rule `pagedRefreshStatus` and `pagedFooter` ask too; `after:` adds rows after the items, such as a board's own place, and `keepsTop:` keeps the screen's top rows over a first page, for choices that start the list again, and `sections:` lays the items out in sections the screen makes of them, such as a batch's months). Filters over a list are segmented `Picker`s and `AppMenuChip`s (a capsule naming the choice that opens an inline picker, filled while it narrows the list) in a `FlowRow` that wraps, since a list cell clips a row scrolled sideways; a board's are drawn from Kotlin's `BoardChoice` (`Screens/RankBoards.swift`: `BoardSegments`, `BoardMenu`, `RankRow`, `YourPlace`), the picker bound to an option's index. `AppIconButton(filled:)` draws the icon's selected form (a starred segment's star). A picture from a URL is `RemoteImage` (Nuke and NukeUI), `Avatar` or `Thumbnail`, never `AsyncImage`: it answers a `heldphoto:` URL (a non-Public gear photo, an upload) from the session's held bytes through `IosApp.heldPhoto`, as Coil's `HeldPhotoFetcher` does; previews and snapshots have no URLs and draw the placeholders. Sheets, menus, alerts (`.alert(_:isPresented:presenting:)` over a state's question, sending its dismiss event when closed), pickers, toggles and pull to refresh are SwiftUI's own; the share sheet is a `UIActivityViewController` that says whether an activity ran (`ArchiveShare`), since `ShareLink` doesn't. Stats come from `@Environment(\.stats)` (the athlete's units, which `SessionView` provides) and labels from `Labels`. Logic beyond layout goes in a small type beside the view with Swift Testing tests (`LoginText`).

- **A native view ships previews and snapshots** (dev/ios-snapshot-tests). Its `#Preview`, inside `#if DEBUG`, shows `SamplePages(Samples.foo) { FooView(state: $0) }` over the screen's samples from `:app-fixtures`, which debug builds export to Swift and release builds don't, so nothing outside `#if DEBUG` names `Samples`. A snapshot suite in `iosApp/iosAppTests` (`LoginSnapshotTests`; `SettingsSnapshotTests` for a screen with a bar, wrapped in a `NavigationStack`, and for a layout at an iPad's size) renders each sample with `assertAppSnapshot`, light and dark. References (`__Snapshots__`) are true for the simulator OS in `Snapshots.recordedOn` (iOS 26.0) and the suites skip elsewhere, so run them there: `xcodebuild test` with an iOS 26.0 simulator as the destination. A first run records and fails, a second compares; look at the new images before committing them, and delete one to rerecord it.
- **Stability.** Every `State` is `@Immutable`, and its collections are `ImmutableList` (kotlinx-collections-immutable; convert with `toImmutableList()` where the presenter loads them), never `List`. Models from non-Compose modules that a UI shows (lexicon views, `AuthCoordinator.Status`) carry `@Immutable` from `androidx.compose.runtime:runtime-annotation`. Composable params must be statically stable, so pass `ImmutableList`s and annotated types, not `List`, `vararg` or plain interfaces (`@Stable` it if one must be a param, like `AppGraph`). `composeStabilityCheck` (part of `check`) enforces this from the compiler reports in `build/compose/stability`; `:app-common-api` and every `-api` module also run it in strict mode, which fails on any field that isn't statically stable.
- **UI tests, previews and samples** (dev/ui-test-harness). A UI renders from its `State` and values a test or preview sets, never from the machine: read the time from `LocalClock` and the zone from `LocalTimeZone` (`ui/Format.kt`), never `Clock.System` or `TimeZone.currentSystemDefault()` (detekt's `NoSystemClockInUi` flags those in `*Ui.kt`), and the 12/24-hour clock through `uses24HourClock()`, which prefers `LocalHourClock`. `AppTheme` takes `darkTheme`. Under `LocalInspectionMode` maps draw `RoutePreview` and Coil images the preview handler's placeholder, so keep new map or image code behind those. `AppPreview` (`:app-common-ui` `ui/preview/`) renders any UI with no session or network, in a chosen platform look, theme, units, `WindowWidth`, time, zone and clock style, and with the real sub-screen UIs when given `subUis = SessionPreviewSubUis` (`composeApp`; the screenshot suite's `ScreenPreview` passes it). It's production code, because `:androidApp`'s screenshot tests use it. Sample states live in `:app-fixtures` (`app/fixtures`, contracts and lexicon only): `fake…` lexicon builders with fixed defaults (`Fixed.NOW`), `ContentStates`/`PagedStates`, and an `XSamples` object per screen in its feature package, with an `all` map keyed by `SampleKind`. UI tests are `runComposeUiTest { setContent { AppPreview { XUi(XSamples.loaded) } } }` in the UI module's `src/jvmTest` (a feature's `-ui` can't see composeApp's `SessionPreviewSubUis`, so another feature's sub-screen renders nothing there, and where its place matters the test passes its own `PreviewSubUis`, like `FeedUploadsUiTest`; only tests spanning features stay in `composeApp/src/jvmTest`, with `subUis = SessionPreviewSubUis`), and find the shared loading pieces and the back button by `TestTags` (`useUnmergedTree = true`), not by text. A new screen ships its samples and a UI test, and a content-loading one joins `ContentLoadingConformanceTest`, which fails for any `State` with a `ContentState` or `PagedState` missing from its table.
- **Screenshot tests** (dev/screenshot-tests). `:androidApp`'s `screenshotTest` suite (AGP test suites, Compose Preview Screenshot Testing, rendered by layoutlib on the host) holds a `XScreenshots.kt` per screen and sub-screen in `androidApp/src/screenshotTest/.../screenshots/`: the loaded sample at `@PreviewScreenSizes` and `@PreviewScreenVariants`, and its other samples at `@PreviewPhoneSize` through an `OtherSamples` provider, all inside `ScreenPreview` (`AppPreview` sized by the preview). Shared components (adaptive controls, loading pieces, charts) render at `@PreviewComponentVariants` in `ComponentPreview`. `check` compares them with the references in `androidApp/src/screenshotTestDefaultDebug/reference`; a change that alters a screen's look reruns `./gradlew :androidApp:updateDebugScreenshotTestDefaultTestSuite` and commits the changed references with it, after looking at them. `ScreenshotCoverageTest` (composeApp jvmTest) fails for a `@CircuitInject` or `@SubCircuitInject` UI, in `composeApp` or any `feature/*/ui`, without its file; a feature's UI module joins the screenshot suite's dependencies. Layoutlib can't render native views, so new map or platform-view code needs an inspection-mode fallback.
- **Tests.** Presenter tests live in the presenter module's `src/jvmTest` and use `Presenter.test {}` or `presenterTestOf` with a Room `inMemoryDatabase()` and a Ktor `MockEngine` (see `LoginPresenterTest`). Use the repo's own (`PresenterTest.kt` in `:app-common-presenter-testing`, which the presenter convention adds to `jvmTest`; root package, no import), never `com.slack.circuit.test`'s: circuit-test composes the presenter on whichever thread resumed it (Room's, Ktor's), racing the test thread, which flakes under load. A reload's loading state shows only if a frame lands before the fake answers, so a test that waits for it after a Retry or Refresh gates the fake (`SessionTestFixture.gate`); otherwise it waits for the state that follows. Fixtures several features' tests share live there too: `SessionTestFixture` (fake PDS and AppView and every repository over them), `ActivityTestBase` (one served activity and the repositories over it, which detail's `ActivityDetailTestBase` extends), `TestZones`, `TestSegments`, `TestRoutes`, `tierOf`; a fixture only one module's tests use stays with them (detail's `ActivityDetailTestBase` and `CombineTestBase`, record's producers over `SessionTestFixture` in `RecordChoices.kt`).
- **Flow tests stay flake-free** (Touchlab's flake-free flow tests). Turbine's timeout is wall-clock time, and Room and the mock AppView answer on real threads, so leave `presenterTestOf`'s `PRESENTER_TEST_TIMEOUT` (core-data's `.test(FLOW_TEST_TIMEOUT)`) alone rather than tuning one test. A state stream (a presenter, `combine`, `stateIn`, a Room flow) may skip an in-between state, so wait for the state you assert with `awaitUntil` rather than taking the next item, and assert a `Loading` only behind a gated fake. Start `test {}` before the action it watches. `expectNoEvents()` and `expectMostRecentItem()` don't wait, so call `testScheduler.runCurrent()` first to let queued recompositions run. Wait on a signal (`awaitUntil`, `join()`, a `CompletableDeferred`), never a fixed `delay` or `Thread.sleep`. ␤
