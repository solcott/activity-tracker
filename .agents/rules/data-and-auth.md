# Client data layer and OAuth

**Room 3**
- Use the `androidx.room3` packages, KSP only. DAO methods must be `suspend` or return `Flow`.
- `core/data/schemas/` is generated by the Room compiler. Never edit it by hand. Changing an entity means bumping `AppDatabase.version` and providing a migration (or an auto-migration); the regenerated schema JSON gets committed with it.
- On the web, Room runs through `web/sqlite-worker` (SQLite WASM on OPFS). That needs the COOP/COEP headers in `webApp/webpack.config.d/devserver.js`. If the web DB silently fails to open, check those headers first.

**Writes go through the outbox.** `ActivityRepository` enqueues each write into the Room `outbox` table with a client-generated TID rkey, so retries are idempotent `putRecord`s. `OutboxProcessor.drain()` applies writes in order and stops at the first failure. GPX track blobs upload first, and their `BlobRef` is spliced into the record. The UI updates optimistically through `FeedRepository.updateCached`. The AppView catches up asynchronously via Jetstream, so never wait for the AppView to reflect a write. Until it does, `FeedRepository` lays its own changes over the AppView's reads: `LocalLikes`, `rewrites` (`LocalRewrites`, a rewritten record) and `deletes` (`LocalDeletes`, deleted activities and comments, and recordings split off a group), so a refresh can't undo them. Photos are the exception to "everything through the outbox": `ActivityManager.edit` and `ActivityRepository.publish` upload a draft's photos (`NewPhoto`, already compressed to WebP by the UI) with `uploadBlob` before queueing the record, so attaching photos needs a connection, while the record itself still goes through the outbox. Until the AppView indexes the record, `LocalRewrites` builds the new photos' views from the athlete's PDS (`ownBlobUrl`). `ActivityManager.delete` removes an activity's record and, through `ActivityStreamsStore.delete`, its streams from every place they could be (deleting a record, or from a space, that isn't there counts as done).

**Activity visibility is where the record is stored** (`activity/Places.kt`). A public activity is a `feed.activity` in the repo; a Followers, Mutuals or Only-me one is the same record, same rkey, in the athlete's tier space for it (`placeOf`), never in the repo. Its streams go to the place for their own visibility, capped at the activity's (`ActivityDraft.publishedStreamsVisibility`); an activity grouped as another recording takes its primary's (`ActivityDraft.recordingOf`), and a primary's recordings share its place.
- **Outbox rows carry a place.** `OutboxEntity.space` (null for the repo) sends a row to that tier space: `OutboxProcessor` ensures the space first (`clients.tiers`, the session's one `AthleteSpaces`, which also announces each tier to the AppView with `notifySpace` once per session), uploads any blob with the ordinary `uploadBlob`, and the space record takes it over. New activities, edits, merges, ungroups and deletes all queue to the activity's place (`ActivityView.visibilityOrPublic`, `OwnActivity.visibility`).
- **Visibility changes are direct calls**, like profile saves: `ActivityManager.setVisibility` and `ActivityRepository.setStreamsVisibility` move records with `moveOwn`, writing the new place before deleting the old (blob refs carry over; nothing is re-uploaded), so a failure leaves the activity stored at least once, shows in the UI, and a retry finishes it. A move drags charts wider than the activity down to it, and moves a primary's recordings too.
- **Likes follow the liked activity's visibility as the view shows it** (`interactionPlaceOf`): a like on a public activity is a `feed.like` in the repo, one on a non-public activity the same record in the athlete's own `interactions` space (`AthleteSpace.INTERACTIONS`, never one of `AthleteSpaces.TIERS`), which only they and the AppView read. A like never moves when the activity's visibility changes; the AppView shows it by the activity's current tier. The PDS lets a session write to a space only the collections its `space:` grant lists (filled in from the space type's declaration at sign-in), so a like on a non-public activity is refused up front with `ScopeMissingError` unless `canWriteToSpaces(feed.like)`: queued, the PDS would refuse it and it would block the outbox. The presenters show that as `UiError.Kind.SignInAgain`. Its URI is repo-style either way, so unliking queues deletes of the rkey from both places (the space one only when `canWriteToSpaces(feed.like)`); a missing record or `SpaceNotFound` counts as done. Comments are placed the same way (`interactionPlaceOf`) and refused up front unless `canWriteToSpaces(feed.comment)`, and a non-public one records the visibility its view showed as `audience`, so the AppView never shows it wider even if the activity is widened. A refused comment's text goes back in the draft (`ActivityDetailPresenter`). Deleting one's own comment (`deleteComment`) queues deletes of its rkey from both places as unliking does (the space one only when `canWriteToSpaces(feed.comment)`), and `LocalDeletes` leaves it out of `FeedRepository.activity`, lowering the count only while the AppView still lists it.
- **Defaults** (`ActivityDefaults`) are the `actor.activityDefaults` record (rkey `self`) in the `self` space, read once per session with the owner's session and Public when unreadable; saving is a direct call that caps the charts default at the activity's.
- **No `space:` scope, no choice.** `SessionClients.canUseSpaces` is false for a session signed in before the scope existed; then a non-public visibility is refused before anything is written (`requireSpacesFor`, `ScopeMissingError`), never published wider. A session from before the space declaration listed `feed.activity` gets `ScopeMissingError` from the PDS instead; both mean signing in again.

**XRPC** is hand-written on Ktor in `core/atproto`. No Ozone or other atproto SDK, because Ozone has no wasmJs target. Call the AppView with `clients.appView.query(X.method, X.Params(...))`. Authentication is a service-auth JWT that the PDS mints via `com.atproto.server.getServiceAuth` (`ServiceAuthAuthenticator`).

**atproto Spaces** (permissioned repos) go through `SessionClients.spaces` (`SpaceClient`, `core/atproto/space`), hand-written like the rest of XRPC. Every Spaces wire type lives in `core/lexicon/.../atproto/Space.kt`, mirrored from the lexicons in the pinned PDS image: the alpha changes weekly, so a bump should touch only that file and `space/`.
- **Owner reads** of the athlete's own repo in their own spaces use the session (DPoP, the `read_self` scope). **Member reads** of anyone else's go to the repo owner's PDS with a credential: `SpaceCredentials` exchanges a delegation token from the viewer's PDS at the authority's PDS, caches it per space until 5 s before `exp`, shares one exchange between concurrent callers, and binds it to an in-memory P-256 key. Both requests carry an RFC 9421 signature (`HttpMessageSignature`, checked against vectors from `@atproto/space`).
- Reads return `SpaceRead`: `Found`, `NotFound`, or `NoAccess` when the authority refuses the viewer. A refusal is an answer, never cached and never an exception, so a new follow counts on the next read. Network and other failures throw. `JwtExpired`/`CredentialRevoked` get one retry with a new credential.
- **Writes** (`createSpace`, which returns `AlreadyExists` instead of failing, `updateSpace`, `putRecord`, `deleteRecord`) go to the athlete's own PDS with the session.
- OAuth asks for the `space:` scope in `OAuthClientConfig.DEFAULT_SCOPE`. A session signed in before a scope or space collection change gets `ScopeMissingError` until the athlete signs in again.
- **Non-public profile details live in the athlete's tier spaces** (`app.activitytracker.space.athlete`, skeys `AthleteSpace.FOLLOWERS`/`MUTUALS`/`SELF`), one `actor.privateDetails` record (rkey `self`) per tier; the tier is the visibility. `ProfileRepository.save` writes a moved detail's new home, then the profile record, then trims old copies, so a failure never loses one. Its `AthleteSpaces` creates a tier's space on the first save that needs it, with the AppView as managing app for reads, and on every save repoints any tier holding details whose managing app is stale (so re-saving lets refused mutuals back in after the AppView's DID changes). A tier record that doesn't decode reads as no details, and the next save replaces it. The managing-app id comes from the AppView's DID document (`SessionClients.managingApp()`), never from `appViewDid`, which on the web is a localhost DID the PDS can't resolve. `profile(actor)` lays tier details under the AppView's public ones: every tier on your own profile, an effectively followed athlete's `followers` and `mutuals` tiers as a member, nothing for anyone else (a pending follower, `viewer.followRequested`, included); a failed read shows public details only. Profile saves are direct calls, not outbox writes: a privacy change that silently retried later would be the wrong failure.
- **Follow requests.** An athlete with `followPolicy: approve` answers requests from `ProfileRepository`. Approving writes a public `graph.followApproval` at rkey = the follower's DID (`putRecord`, so it's idempotent); removing a follower deletes it. Declining writes `graph.followDecline` to the athlete's `self` space only, so the AppView never learns of it: `followRequests()` reads the AppView's pending list (declines included) and splits off the athlete's declines itself. A DID that isn't a valid record key can't be answered (`canAnswer`). Turning approval on (`ProfileEdit.followPolicy`) pages the athlete's followers and `applyWrites` the approvals they lack, 200 at a time, before the profile record gets the policy, so a failure leaves it open and a retry writes only the rest. `PendingFollows` shows a follow of an approve-policy athlete as requested, with no count change, until the AppView indexes it.

**Logging.** Shared and client code logs with Kermit, never `println`. Take a Kermit `Logger` in the constructor (Metro provides it in `AtprotoBindings`) and keep `logger.withTag("ClassName")`; don't call the global `Logger` directly. Use the lambda overloads. Tests pass `Logger(loggerConfigInit(TestLogWriter(...)))` from `kermit-test`. `createHttpClient(logger)` installs HTTP logging only when given a logger. Never log tokens, DPoP keys, or record contents. The AppView logs with SLF4J; its `Slf4jLogWriter` routes Kermit output from `core-atproto` into Logback.

**OAuth** (`core/atproto/oauth`) is a full ATProto public client: handle → DID → PDS → authorization server, then PAR + PKCE + DPoP with nonce retry, then refresh.
- Pending authorizations are persisted *before* the browser opens, because the web redirect unloads the page. Redirects come back to `AuthCoordinator.handleRedirect`: from the `MainActivity` intent filter on Android, the `ASWebAuthenticationSession` callback on iOS, and URL params in `webApp`'s `main.kt` on the web.
- Web uses the loopback client ID. Loopback redirects must use `127.0.0.1`, so the web app redirects from `localhost`.
- Native clients use the AppView-hosted `/oauth/client-metadata.json` over an HTTPS tunnel. The only knob is `activitytracker.appviewPublicUrl` (`local.properties`). The `activitytracker.native.oauth` convention plugin derives the redirect scheme from it for `GeneratedNativeNetworkConfig`, the Android manifest and the AppView `run` task. Don't hard-code a scheme or client ID anywhere.
- Stored OAuth state is encrypted with a platform `SecretCipher` (Keystore, Keychain, WebCrypto). Tests use `InMemorySecretCipher`.
