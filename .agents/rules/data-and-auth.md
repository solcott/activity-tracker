# Client data layer and OAuth

**Room 3**
- Use the `androidx.room3` packages, KSP only. DAO methods must be `suspend` or return `Flow`.
- `core/data/schemas/` is generated by the Room compiler. Never edit it by hand. Changing an entity means bumping `AppDatabase.version` and providing a migration (or an auto-migration); the regenerated schema JSON gets committed with it.
- On the web, Room runs through `web/sqlite-worker` (SQLite WASM on OPFS). That needs the COOP/COEP headers in `webApp/webpack.config.d/devserver.js`. If the web DB silently fails to open, check those headers first.

**Writes go through the outbox.** `ActivityRepository` enqueues each write into the Room `outbox` table with a client-generated TID rkey, so retries are idempotent `putRecord`s. `OutboxProcessor.drain()` applies writes in order and stops at the first failure. Blobs (a track's GPX, a streams record's data) upload first, and their `BlobRef` is spliced into the record. A blob several writes share (`PendingBlob.key`: a logbook's original file, named by each of its dives' `feed.activitySource`) is stored once in `outbox_blob` (`OutboxBlobEntity`, rows name it by `blobKey`), uploaded once, and its ref saved after the first put succeeds so later rows reuse it (a `BlobNotFound` on a reused ref uploads it once more); it's deleted once no pending row names it. The one write dropped instead of retried is a `feed.activitySource` whose blob the PDS refuses as too large (`413 PayloadTooLarge`): it's logged and the drain goes on, so the activity just has no original. The UI updates optimistically through `FeedRepository.updateCached`. The AppView catches up asynchronously via Jetstream, so never wait for the AppView to reflect a write. Until it does, `FeedRepository` lays its own changes over the AppView's reads: `LocalLikes`, `rewrites` (`LocalRewrites`, a rewritten record), `deletes` (`LocalDeletes`, deleted activities, and recordings split off a group) and `localComments` (`LocalComments`, comments sent, deleted, hidden or unhidden), so a refresh can't undo them. Photos are the exception to "everything through the outbox": `ActivityManager.edit` and `ActivityRepository.publish` upload a draft's photos (`NewPhoto`, already compressed to WebP by the UI) with `uploadBlob` before queueing the record, so attaching photos needs a connection, while the record itself still goes through the outbox. `upload` keeps each photo's bytes by blob CID in `FeedRepository.heldPhotos` (`HeldPhotos`, for the session), and until the AppView serves a photo, `LocalRewrites` (`mediaViews`) shows it from them under a `heldphoto://blob/{cid}` URL, which `composeApp`'s `HeldPhotoFetcher` answers. The PDS's public `sync.getBlob` (`ownBlobUrl`) is only a fallback for a public activity's photo whose bytes aren't held: it refuses a blob only a tier space holds. A non-public photo without held bytes keeps its held URL and shows as a placeholder. A photo is matched to the AppView's view by `photoCid` (the URL's last path segment), since a non-public one's URL is signed for the viewer, and `FeedRepository` drops held bytes once the AppView serves them. `ActivityManager.delete` removes an activity's record, its track (`ActivityTrackStore.delete`) and, through `ActivityStreamsStore.delete`, its streams from every place they could be (deleting a record, or from a space, that isn't there counts as done).

**Activity visibility is where the record is stored** (`activity/Places.kt`). A public activity is a `feed.activity` in the repo; a Followers, Mutuals or Only-me one is the same record, same rkey, in the athlete's tier space for it (`placeOf`), never in the repo. A legacy group's recordings (`recordingOf`) share their primary's place, as a combined activity's members share its.
- **Detail categories split an activity by tier** (`DetailCategory` in `core/lexicon`, `ActivityLayout`). Each of ten categories (start time, heart rate, power, pace/speed, calories, map, physiology, cadence, dive, gear) has its own visibility, capped at the activity's (`VisibilityChoice.tiers`), a category never set starting at the activity's except gear, which starts at Only me (`DetailCategory.defaultWhenUnset`); every summary field, stream channel and lap/leg field is in one category or core, and core data stays at the activity's tier. `ActivityLayout.split` makes the `feed.activity` record without narrower categories' fields (a hidden start becomes the local day's midnight, a hidden map drops the polyline), one `feed.activityDetails` per narrower tier (never in the repo), and one `feed.activityStreams` per tier holding channels, each with its own blob (`PdsActivityStreamsStore`, halved once before the split so every part shares one time array). A new activity queues details narrowest first, then the record, then streams narrowest first. A narrower category needs `canWriteToSpaces(feed.activityDetails)` (`requireDetailsSpaceFor`), refused up front without it. Readers use `ActivityView.effectiveRecord()` (the record with `details` laid over it) and the AppView's merged streams; `DetailCategory.currentTiers` reads each category's tier back from `details` and the streams' `parts`. An activity from before categories keeps its core channels in its one streams record (`ActivityStreams.core`). Its full-resolution track is never part of the activity record: it's a `feed.activityTrack` (`ActivityTrackStore`) always in the `self` space, whatever the activity's visibility, which visibility changes never move and the AppView ignores. Publishing a GPX is refused up front unless `canWriteToSpaces(feed.activityTrack)` (`requireTrackSpace`). An import's devices and their serial numbers (`feed.activityDevices`, `ActivityDevicesStore`, from `ActivityDraft.devices`) live in `self` the same way, queued after the activity and its original, untouched by visibility changes, kept by each member of a combined activity (which has none of its own) and deleted with it; unlike tracks and originals, a session that can't write them skips them instead of refusing the import.
- **Combined activities are built on the client, and members are never rewritten** (`feed/combined-activities`). `ActivityManager.combine` drains the outbox, moves the other activity to the combined one's visibility (`follow`, as recordings move with their primary), reads every member from every place (`ActivityPlaces.read`) with its `self` track, and `ActivityCombiner` builds the combined record, streams and route: per channel, each moment from the highest-ranked member with a sample then (`combined.sources`, default most samples first), distance carried on at a handover, members recorded one after another as legs. The combined activity is written like any other (details, record, streams, a multi-`trkseg` track) under a new TID, or under its own rkey when rebuilt (adding or removing a member), keeping its title, photos, ranking and categories; a new one takes each category at the narrowest any member has. Its polyline is `RouteTrim.segmentedPolylineOf`: the route cut wherever no position was recorded for two minutes, each piece trimmed on its own, the breaks in `polylineGaps`, and `RouteTrimmer` re-trims combined activities the same way. Splitting deletes only the combined activity; deleting a member rebuilds it or splits it at one member left. `LocalDeletes.combine` hides members from lists until the AppView catches up. An import combines without waiting for the AppView: `combine(into: OwnActivity, drafts)` publishes the drafts at the logged activity's visibility (`ActivityDraft.atVisibility`) and builds from their own record, streams, route and zones plus the logged member as stored (refused while it's unsent), and `combine(drafts)` builds from drafts only.
- **Outbox rows carry a place.** `OutboxEntity.space` (null for the repo) sends a row to that tier space: `OutboxProcessor` ensures the space first (`clients.tiers`, the session's one `AthleteSpaces`, which also announces each tier to the AppView with `notifySpace` once per session), uploads any blob with the ordinary `uploadBlob`, and the space record takes it over. New activities, edits, combines, ungroups and deletes all queue to the activity's place (`ActivityView.visibilityOrPublic`, `OwnActivity.visibility`).
- **Visibility changes are direct calls**, like profile saves: `ActivityManager.setVisibility` reads the activity from every place (`ActivityPlaces.read`, record, details and streams with their blobs, straight from the PDS) and saves the new layout in two phases (`ActivityPlaces.save`): narrowest place first, each place takes the union of what it holds and what it will hold; then widest first, each is cut to what it will hold and records it won't hold are deleted. Changed streams get new blobs. A failure leaves every field stored at least once, shows in the UI, and saving again finishes it. A primary's recordings move with it, keeping their categories unless now wider. Before the first save of an activity from before categories would make its core charts wider, `coreChartsWiden` lets the edit screen ask. Once a session `ActivityPlaces.repairOnce` (from `repairZones`) finishes split activities an interrupted save left in two places, never widening.
- **Zones are a record of their own** (`feed.activityZones`, `ActivityZonesStore`), stored at the narrowest of the heart rate tier, the power tier (`zonesTier`) and the training's visibility (`ZonesPlacement.target`), because zone bounds reveal thresholds. `PdsActivityStreamsStore` hands them over: `put` queues them at the training as read fresh from the PDS and tier spaces (`ownTrainingVisibility`; Only me when unreadable, dropped when the session can't write them to that space), `ActivityManager.setVisibility` moves them first when the heart rate or power tier changes (wider only up to the training), and `delete` clears them everywhere. Narrowing training fails toward narrower: `ProfileRepository.save` calls `TrainingNarrowing.narrowTo` first, which sends queued zones writes (`OutboxProcessor.drain(only)`, so a write stuck elsewhere can't block it), queues a put-then-delete move for every zones record stored wider (skipping rkeys already queued), sends those, and throws `PendingWritesException` (`UiError.Kind.WritesPending`) if any is left, so the training keeps its old visibility while the queued moves finish later. Setting training where none is saved counts as narrowing from Public. Widening or clearing training moves nothing. A batch import reads the training once (`withTrainingReadOnce`). A heart rate or power move moves zones first and throws when the session can't write them where they go. Once a session, `FeedPresenter` runs `ActivityRepository.repairZones` (`sweepOnce`) apart from the feed load and the route sweep, which moves zones wider than their heart rate and power tiers (read from streams channels and details; an old activity's one streams record stands for both) and the current training allow and drops copies an interrupted move left behind, never widening. Moves, the backfill and the sweep share one lock.
- **Likes follow the liked activity's visibility as the view shows it** (`interactionPlaceOf`): a like on a public activity is a `feed.like` in the repo, one on a non-public activity the same record in the athlete's own `interactions` space (`AthleteSpace.INTERACTIONS`, never one of `AthleteSpaces.TIERS`), which only they and the AppView read. A like never moves when the activity's visibility changes; the AppView shows it by the activity's current tier. The PDS lets a session write to a space only the collections its `space:` grant lists (filled in from the space type's declaration at sign-in), so a like on a non-public activity is refused up front with `ScopeMissingError` unless `canWriteToSpaces(feed.like)`: queued, the PDS would refuse it and it would block the outbox. The presenters show that as `UiError.Kind.SignInAgain`. Its URI is repo-style either way, so unliking queues deletes of the rkey from both places (the space one only when `canWriteToSpaces(feed.like)`); a missing record or `SpaceNotFound` counts as done. A comment is placed by its audience, not the activity's visibility: `commentAudience` is the visibility the view shows for a top-level comment, and for a reply (`comment(…, replyTo)`) the narrower of that and the parent's `audience` (`Visibility.narrower`), so a reply never reaches viewers its parent was hidden from. A Public audience goes in the repo, any other in the `interactions` space (`interactionPlaceOf`), refused up front unless `canWriteToSpaces(feed.comment)`; so a reply to a Followers comment on an activity since made Public stays out of the repo. A non-public comment records its audience as `audience`, so the AppView never shows it wider even if the activity is widened. A reply's `reply` names the parent and its thread's root (`replyTo.root ?: replyTo`), both strong refs, so a comment the AppView hasn't listed (a `SentComment`, which has no CID) can't be replied to. A refused comment's text, and the comment it replies to, stay in the draft (`ActivityDetailPresenter`). A sent comment (`comment`, which returns its URI) is listed after the loaded comments, or a sent reply (`SentComment.root`) at the end of its thread, and counted at once (`LocalComments.sent`) until the AppView lists it. Deleting one's own comment (`deleteComment`) queues deletes of its rkey from both places as unliking does (the space one only when `canWriteToSpaces(feed.comment)`), and `LocalComments` leaves it out of every page for the session, lowering the count only while the AppView still counts it, and never for a hidden comment, which it doesn't. An athlete hides someone else's comment on their own activity (`setCommentHidden`) with a `feed.commentHide` placed the same way (`interactionPlaceOf`, refused up front unless `canWriteToSpaces(feed.commentHide)`), at rkey `commentHideRkey(comment)` (`core/atproto`, a SHA-256 of the comment's URI, so it suspends), so a repeat is the same record and unhiding deletes that rkey from both places with no lookup, the space one only with the scope. `LocalComments` marks the comment and moves the count by the difference from the AppView's answer until it catches up. It holds each change as what the viewer wants of the comment against what the AppView last said of it. Pages (`FeedRepository.comments`: pages of threads, or with `root` a thread's replies) report every comment and reply the AppView lists, `LocalComments.applyTo(thread)` lays the changes over a thread's top-level comment and replies alike (a deleted top-level comment leaves a placeholder), and replies count like any comment, and `FeedRepository.activity` asks `getComments` by `uris` about an activity's unsettled changes alongside `getActivity`, so the count is right without loading every page. Each change is recorded before its write is queued and taken back if queueing throws.
- **Privacy zones trim every polyline before it's written** (`PrivacyZones`, `RouteTrimmer`). The zones and the hide-start/end distance are one `actor.privacyZones` record (rkey `self`) in the `self` space, a new `revision` TID on each save; a new zone's stored center is offset by up to half its radius (`PrivacyCircle.offsetCenter`) and the point chosen is never stored. `ActivityDraft` carries the full `route`, never a polyline: `ActivityRepository.queue` builds the record's polyline with `RouteTrim.polylineOf` (`TrackMath.trim` on the whole route, then `ActivityDraft.polylineOf`, which breaks it with `RouteBreaks` where positions were recorded over the gap limit and 200 m apart, the breaks in `polylineGaps`), at every visibility, Only me included. `PrivacyZones.forPublish` reads fresh for each publish (once per batch with `withReadOnce`), falls back to the last read this session, and with none is `RouteTrim.Unknown`, which writes no polyline: never an untrimmed one. A record that doesn't decode is `Unknown` too. Activities published without a fresh read are remembered for the session and trimmed again once the zones are read (`RouteTrimmer.trimStale`, from `publish` and `sync`). When the zones change, `RouteTrimmer.sweep` rewrites the polyline of every activity with a track, at every place, from the track in `self` (`ActivityTrackStore.read`, `readGpxTrack`), and of activities whose activity and track are both still queued (from the queued GPX), changing only `polyline` and `polylineGaps`. It sends those rewrites, then writes `actor.routeTrim` (the revision done) only if none is left pending, so an interrupted sweep finishes in a later session on any device; a separate record so a sweep never overwrites a zone saved meanwhile. `FeedPresenter` runs it once a session (`repairRoutes`), and `App` collects `repairRoutesOnSave` for the session, so a save's sweep outlives the settings screen. `ActivityManager.edit` and `ungroup` start from the outbox's last queued put of the record (`queuedActivityRecord`), so they never undo a queued re-trim. Saving zones is a direct call. The owner's detail map draws the full track (`ActivityRepository.ownRoute`); everyone else sees the trimmed polyline.
- **Segment tracks** (`data/segments`) give the AppView matchable routes only with consent. `SegmentPrefsRepository` is the `actor.segmentPrefs` record (rkey `self`) in `self`: no record means never asked (the feed asks once, `shouldAsk`), a read failure is unknown and counts as off, and saving is a direct call that sets `saved`. While it's on, `SegmentTracks` queues a `feed.segmentTrack` (`SegmentTrackStore`, in `self`, a JSON blob of E7 positions and seconds from the track's start, never wall-clock time) beside each full track as it's published or combined, cut by `PrivacySettings.pieces` (`TrackMath.trimPieces` after the polyline's breaks: a pass through a zone is two pieces, never a chord), and deletes it with the activity. It's never written untrimmed: zones never read this session write none, and one trimmed by the last read rather than a fresh one carries that revision and makes `sync` sweep. `SegmentTrackSweeper` lists tracks and segment tracks in `self` and writes each that's missing or carries another `zonesRevision` (on), or deletes them all (off). There's no marker: whatever an interrupted sweep left still differs. It runs after `RouteTrimmer.sweep` in `repairRoutes` and on every zone save, and after every save of the setting (`repairRoutesOnSave`).
- **Leaderboard brackets** (`LeaderboardBracketsRepository`, segments/leaderboard-brackets) are the athlete's consent to age, weight and gender boards: an `actor.leaderboardBrackets` record (rkey `self`) in `self` that exists only while it's on (saving off deletes it, a missing record or space counting as done) and holds only `LeaderboardBrackets.of(details, today)`, never the details, read from every tier (`ProfileRepository.ownProfile`). Saves are direct calls; `canUse` hides it from sessions whose grant predates the record. `App` runs `refreshOnSave` for the session: once at its start (a birthday) and after each `ProfileRepository.save` (`savedDetails`), it rewrites the record while on and only when a bracket changed, logging a failure for the next session.
- **Defaults** (`ActivityDefaults`) are the `actor.activityDefaults` record (rkey `self`) in the `self` space, read once per session with the owner's session and Public when unreadable: the activity's visibility and one per detail category (`details`), a category never set starting at the activity's (gear at Only me) and an old `chartsVisibility` ignored. **Gear defaults** (`GearDefaults`) are the `gear.autoAssign` record (rkey `self`) in `self`: per sport and sub-sport, the items a new activity starts with (`forType`: for each gear type a sub-sport entry's items beat the sport's, retired and deleted items skipped); a session whose grant predates the record is refused with `SCOPE_MISSING`. The same record holds the athlete's sensor links, profile links and ignored devices (gear/gear-sensors), keyed by `SensorKey` (serial, else ANT IDs, else a weak maker and model), so serials stay in `self`; `GearDefaults.editLinks` keeps a key in at most one of links and ignores. An import's untouched gear is `GearAutoAssign.resolve`: per gear type, linked sensors' items lifted to what they were mounted on at the start (`GearMounts.rootAt`), else the profile's, else the defaults, with clashes reported. Import keys come from `ImportedDevice.toActivityDevice()`, the stored form, so they match `ActivityDevicesStore.list()`; `PastImportsMatcher` adds a new link's item to earlier imports through `ActivityManager.setVisibility`, skipping any already listing that gear type, so a rerun resumes. **Gear collections** (`GearCollections`) are `gear.collection` records (TID rkeys) in `self` only, membership stored on the collection; `all(items)` hides members whose items are gone, `GearRepository.delete` then removes the item from every collection (best effort), and the picker's `GearEvent.AddCollection` adds a collection's active members to the selection, never a reference to the collection. An activity's gear is the `gear` summary field (`ActivityDraft.gear`), placed by its Gear category like any other; an edit changes it through `ActivityManager.setVisibility(…, gear)`, which rewrites every place, so a narrower Gear category never touches the activity record. Saving is a direct call that caps each category at the activity's.
- **No `space:` scope, no choice.** `SessionClients.canUseSpaces` is false for a session signed in before the scope existed; then a non-public visibility is refused before anything is written (`requireSpacesFor`, `ScopeMissingError`), never published wider. A session from before the space declaration listed `feed.activity` gets `ScopeMissingError` from the PDS instead; both mean signing in again. **No Spaces on the PDS, no choice either:** `App` calls `SessionClients.resolveSpacesSupport()` at session start, which reads the PDS's `describeServer` once for the Spaces alpha's temporary `spacesAlpha: true` (`SpacesSupport`). A PDS that answers without it is `Unsupported`: `canUseSpaces` and `canWriteToSpaces` are false whatever the scope, the pickers say the server can't (`VisibilityFields.spacesUnsupported`, from `ActivityDefaults.spacesUnsupported`), and a non-public save is refused with `SpacesUnsupportedException` (`requireSpacesFor`, `requireInteractionsFor`, `gearRefused`), shown as `UiError.Kind.SpacesUnsupported`, never as signing in again. A failed lookup, and the time before it answers, is `Unknown`, and the scope decides. Each alpha bump checks the new image's `describeServer` still has the flag; when upstream drops it, delete `spacesSupport`, `resolveSpacesSupport` and its line in `canUseSpaces`/`canWriteToSpaces`, and `SpacesUnsupportedException` with its mappings.

**Reads that screens load return `Flow<Outcome<T>>`** (`io.github.solcott:dataresult`). Build them with `outcomeFlow { … }` for a network read (`SegmentRepository.segmentOutcome`), or `cachedOutcomes(cache, isEmpty) { refresh() }` for a Room cache and the refresh that rewrites it (`FeedRepository.timelineOutcomes`): it holds an empty cache back while the refresh runs, so a first visit shows loading rather than an empty list. Both classify failures in one place (`Throwable.toDataError`, `OutcomeOf.kt`): `XrpcException` becomes `Api` with its error name, or `Http` for a non-XRPC body; any `IOException`, Ktor's timeouts included, is `Network`, and so is a rejected `fetch` on the web, which Ktor reports as a `JsError` (`isPlatformNetworkFailure`); a decoding failure is `Serialization`. Never surface a raw exception or its message past a repository read. Paged lists read a page as `Outcome<Page<T, M>>` (`uistate`'s `Page`) through `outcomeOf`, beside the throwing read it wraps (`BlockRepository.blocksPage`, `FeedRepository.commentsPage`). Writes and actions keep throwing (`runSuspendCatching`).

**XRPC** is hand-written on Ktor in `core/atproto`. No Ozone or other atproto SDK, because Ozone has no wasmJs target. Call the AppView with `clients.appView.query(X.method, X.Params(...))`. Authentication is a service-auth JWT that the PDS mints via `com.atproto.server.getServiceAuth` (`ServiceAuthAuthenticator`).

**atproto Spaces** (permissioned repos) go through `SessionClients.spaces` (`SpaceClient`, `core/atproto/space`), hand-written like the rest of XRPC. Every Spaces wire type lives in `core/lexicon/.../atproto/Space.kt`, mirrored from the lexicons in the pinned PDS image: the alpha changes weekly, so a bump should touch only that file and `space/`.
- **Owner reads** of the athlete's own repo in their own spaces use the session (DPoP, the `read_self` scope), with no credential or MAC. **Member reads** of anyone else's go to the repo owner's PDS with a credential: `SpaceCredentials` exchanges a delegation token from the viewer's PDS at the authority's PDS in an unauthenticated POST whose body also names a fresh P-256 key (`credentialKid`), so every credential has its own in-memory key (`Credential.key`). It caches each per space until 5 s before `exp` and shares one exchange between concurrent callers. Reads send `Authorization: Atproto-Space-Credential <cred>` and `Atproto-Space-Audience` (the repo owner), with an RFC 9421 signature by the credential's key (`HttpMessageSignature`: label and tag `atproto-space-credential`, padded base64, checked against vectors from `@atproto/space`).
- **Read MACs.** A member's `getRecord` (`SpaceMember.getRecord`) and the AppView's `listRepoOps` (`SpaceMember.listRepoOps`) send `Atproto-Space-Want-Mac` and return a response only once its `Atproto-Space-Mac` verifies: `SpaceMac` (`forCommit`, `forRecord`, a `SpaceMacResult`), keyed through `SpaceKem`, ECDH against the author's `#atproto_kem` (`DidDocument.kemKey`, cached in `SpaceCredentials.kemKey`) then HKDF, read with `XrpcClient.queryWithHeaders`. A record must come back at the URI asked for (`<space>/<repo>/<collection>/<rkey>`), a commit must name the space and repo asked for. A failed check re-resolves the owner's DID document (`kemKey(refresh = true)`) and tries once more, then throws `SpaceMacException`, which isn't an `XrpcException`, so `SpaceRead` never reports it as no access: it's a failure. Each call agrees a fresh ephemeral key, so make one per request, retries and pages included. The shared secret never leaves the verifier: never log or cache it. The MAC covers a commit's `data` and a record's URI and CID (`Cid.bytes()`), not its value; nothing checks a value against its CID. `listRecords`, `getBlob` and `registerNotify` carry no MAC. `SpaceMacHost` is the host's side (decapsulate, `Atproto-Space-Mac`), for test fakes only. Vectors from `@atproto/space` are in `SpaceMacVectors`, regenerated on each alpha bump.
- Reads return `SpaceRead`: `Found`, `NotFound`, or `NoAccess` when the authority refuses the viewer. A refusal is an answer, never cached and never an exception, so a new follow counts on the next read. Network and other failures throw. `JwtExpired`/`CredentialRevoked` get one retry with a new credential.
- **Writes** (`createSpace`, which returns `AlreadyExists` instead of failing, `updateSpace`, `putRecord`, `deleteRecord`) go to the athlete's own PDS with the session.
- OAuth asks for the `space:` scope in `OAuthClientConfig.DEFAULT_SCOPE`. A session signed in before a scope or space collection change gets `ScopeMissingError` until the athlete signs in again.
- **Non-public profile details live in the athlete's tier spaces** (`app.activitytracker.space.athlete`, skeys `AthleteSpace.FOLLOWERS`/`MUTUALS`/`SELF`), one `actor.privateDetails` record (rkey `self`) per tier; the tier is the visibility. `ProfileRepository.save` writes a moved detail's new home, then the profile record, then trims old copies, so a failure never loses one. Its `AthleteSpaces` creates a tier's space on the first save that needs it, with the AppView as managing app for reads, and on every save repoints any tier holding details whose managing app is stale (so re-saving lets refused mutuals back in after the AppView's DID changes). A tier record that doesn't decode reads as no details, and the next save replaces it. The managing-app id comes from the AppView's DID document (`SessionClients.managingApp()`), never from `appViewDid`, which on the web is a localhost DID the PDS can't resolve. `profile(actor)` lays tier details under the AppView's public ones: every tier on your own profile, an effectively followed athlete's `followers` tier as a member, and their `mutuals` tier too only when they effectively follow back (`viewer.followedBy`, so a one-way follower skips a refusal that would cost an exchange every view; a follow-back shows once the AppView indexes it), nothing for anyone else (a pending follower, `viewer.followRequested`, included); a failed read shows public details only. Profile saves are direct calls, not outbox writes: a privacy change that silently retried later would be the wrong failure.
- **Follow requests.** An athlete with `followPolicy: approve` answers requests from `ProfileRepository`. Approving writes a public `graph.followApproval` at rkey = the follower's DID (`putRecord`, so it's idempotent); removing a follower deletes it. Declining writes `graph.followDecline` to the athlete's `self` space only, so the AppView never learns of it: `followRequests()` reads the AppView's pending list (declines included) and splits off the athlete's declines itself. A DID that isn't a valid record key can't be answered (`canAnswer`). Turning approval on (`ProfileEdit.followPolicy`) pages the athlete's followers and `applyWrites` the approvals they lack, 200 at a time, before the profile record gets the policy, so a failure leaves it open and a retry writes only the rest. `PendingFollows` shows a follow of an approve-policy athlete as requested, with no count change, until the AppView indexes it.

**Logging.** Shared and client code logs with Kermit, never `println`. Take a Kermit `Logger` in the constructor (Metro provides it in `AtprotoBindings`) and keep `logger.withTag("ClassName")`; don't call the global `Logger` directly. Use the lambda overloads. Tests pass `Logger(loggerConfigInit(TestLogWriter(...)))` from `kermit-test`. `createHttpClient(logger)` installs HTTP logging only when given a logger. Never log tokens, DPoP keys, or record contents. The AppView logs with SLF4J; its `Slf4jLogWriter` routes Kermit output from `core-atproto` into Logback.

**OAuth** (`core/atproto/oauth`) is a full ATProto public client: handle → DID → PDS → authorization server, then PAR + PKCE + DPoP with nonce retry, then refresh.
- Pending authorizations are persisted *before* the browser opens, because the web redirect unloads the page. Redirects come back to `AuthCoordinator.handleRedirect`: from the `MainActivity` intent filter on Android, the `ASWebAuthenticationSession` callback on iOS, and URL params in `webApp`'s `main.kt` on the web.
- Web uses the loopback client ID. Loopback redirects must use `127.0.0.1`, so the web app redirects from `localhost`.
- Native clients use the AppView-hosted `/oauth/client-metadata.json` over an HTTPS tunnel. The only knob is `activitytracker.appviewPublicUrl` (`local.properties`). The `activitytracker.native.oauth` convention plugin derives the redirect scheme from it for `GeneratedNativeNetworkConfig`, the Android manifest and the AppView `run` task. Don't hard-code a scheme or client ID anywhere.
- Stored OAuth state is encrypted with a platform `SecretCipher` (Keystore, Keychain, WebCrypto). Tests use `InMemorySecretCipher`.
